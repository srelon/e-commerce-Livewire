# Database Schema — Shop Domain

Reference for the tables added on top of the initial RBAC scaffold (`users`, `admins`, `admin_roles`, `admin_accesses`). All shop-domain tables use `timestamps()` + `softDeletes()`.

**Manual ordering always uses `sort_order`** (`unsignedInteger`, default `999`) — never `sort`, `order`, or `position`. Every table with a manual-order column uses this exact name (`products_categories`, `product_images`, `product_stocks`, `menus`), including `menus` where it's remapped from the `solution-forest/filament-tree` package's own `order` config key (see § Navigation).

Migrations: `backend/database/migrations/2026_07_02_*`. Models: `backend/app/Models/*`.

## Catalog

**products_categories** *(model `ProductsCategory`, table renamed from `categories` to avoid confusion with `news_categories`)* — `name, slug, icon, image, sort_order, status`. Product count is never stored, always `products()->count()`.

**products_authors** *(model `ProductsAuthor`, table renamed from `authors` for the same reason as `products_categories`)* — `name, slug, avatar_color, photo, content`. Same idea — `books` is `products()->count()`, not a column.

**products** — `category_id → products_categories`, `author_id → products_authors`, `title, slug, short_description, description, rating_avg, reviews_count, bestseller, status, published_at`.
Price and stock are **not here** — see `product_stocks`. For product cards/pages, always read price/availability off `Product::activeStock` (the row with `status = 1`) — never add a price column back onto `products`.
**`rating_avg` is nullable, no seeded default** — `null` means the product has no reviews yet, not a 0-star rating. `ReviewService::recalculateRating()` sets it back to `null` (not `0`) once the last review is deleted. Every read path (`ProductService::formatProduct()`/`formatProductDetail()`, the websocket review-event payload) passes `null` through as-is instead of casting it to `(float) 0`, and the frontend hides all rating UI (`book-card__rating-badge`, `StarRating`, `RatedCard`'s stars) when `rating` is `null`.

**product_images** — `product_id → products, image, sort_order`.

**Image columns are JSON, not a single path string** — `products_categories.icon`, `products_categories.image`, `products_authors.photo`, `product_images.image`, `news_posts.image` all store an object of size/format variants (e.g. `{"original": "...", "thumb": "..."}`) cast to `array` on the model, rather than one plain path. Exact variant keys aren't finalized yet — decide when the upload/image-processing service gets built.

**product_stocks** — a batch/lot system for inventory, not a single column on the product:
`product_id → products, quantity, price, before_price (nullable, pre-discount price), real_price (purchase/cost price), sort_order (default 999), status`.
A product can have several rows at once: one `active` (currently on sale), others `queued` (next batch at a different price), old ones `fulfilled`/`cancelled`. `order_items` points at a specific row (`product_stock_id`), so price and stock are decremented against the exact batch, not the product in general.

## Reviews and notifications

Ported almost 1:1 from another existing project (its `comments`/`comment_likes`/`comment_reports`/`user_notifications` tables), with `comment_id → review_id`. The moderation/likes/notifications logic for that structure is already built and working there, so it wasn't redesigned here.

Unlike the source project, `reviews` is **not** product-specific — it's polymorphic (`type`/`record_id`, aliased through the same morph map as `seo_meta`) so it can be reused for any content, not just `products`. `Product::reviews()` and `NewsPost::reviews()` are both `morphMany(Review::class, 'reviewable', 'type', 'record_id')`, sharing one table instead of duplicating the whole structure per content type.

**reviews** *(= `comments`, model `Review`)* — `type, record_id (the reviewed record — e.g. type "products" + a product id), user_id (nullable, nullOnDelete — but a row can only be created while authenticated, there is no guest path), parent_id (self, replies), replied_to_comment_id, rating (nullable, only on the root review — the one field that wasn't in the original), body, status, deleted_by`.

**review_likes** *(= `comment_likes`, model `ReviewLike`)* — `review_id, user_id, opp_type`, unique(`review_id, user_id`).

**review_reports** *(= `comment_reports`, model `ReviewReport`)* — `review_id, user_id, reason`, unique(`review_id, user_id`).

**user_notifications** *(model `UserNotification`, `SoftDeletes`)* — `user_id, from_user_id (nullable, no FK), type (reply/like/dislike/system), data (json), product_id (nullable), review_id (nullable), parent_id (nullable, root review, no FK), read_at`.

### Notifications API (2026-07-05)

`App\Services\NotificationService` — triggered from `ReviewService::create()` (a reply) and `ReviewService::toggleReaction()` (like/dislike), never from a controller directly.

- **Reply**: replying to a root review notifies that review's owner, unless the replier owns it themselves (no self-notification). `type: 'reply'`, `data: {from_name, review_preview}` (`review_preview` is the reply's own sanitized body, truncated to 100 chars), `review_id` = the new reply's id, `parent_id` = the root's id.
- **Like/dislike**: reacting to any review or reply notifies its owner (unless reacting to your own). Reuses **one row per (owner, review_id, from_user_id)** via `upsertReaction()` — switching from like↔dislike updates that same row in place (and deliberately does **not** reset `read_at`, so an already-read notification whose reaction later changes doesn't reappear as unread) — toggling the reaction off entirely (`opp_type → 0`) calls `deleteReaction()`, which **soft-deletes** the row (the table has `SoftDeletes`, matching `reviews`/`review_likes`) rather than a hard delete.
- `type: 'system'` is defined but nothing currently triggers it — an extensibility point only, ported as-is.

**`GET /api/notifications`** *(`auth:sanctum`)* — top 10 latest, **auto-marks them read** as a side effect of fetching, returns `{items, unread_count}` where `unread_count` is what remains unread *after* that auto-mark (i.e., excludes the batch just marked).

**`GET /api/notifications/all`** *(`auth:sanctum`)* — paginated (20/page), same auto-mark-on-fetch behavior per page.

**`GET /api/notifications/unread-count`** *(`auth:sanctum`)* — `{count}`, no side effects (doesn't mark anything read).

**`PATCH /api/notifications/{id}/read`** *(`auth:sanctum`)* — marks one notification read; idempotent, ownership-checked (`$user->userNotifications()->whereKey($id)` — silently no-ops for another user's id or an already-read one, no error).

**Real-time transport** — same pattern and envelope as reviews: `Redis::publish("notifications.users.{$user_id}", json_encode(['event' => 'notification', 'data' => $payload]))` — the `{event, data}` wrapper matters, not just a detail: the frontend's `stores/websocket.ts` has one generic `onmessage` handler shared by every channel that destructures `{event, data}` and re-dispatches `ws:{event}`, so a payload missing that envelope (an earlier draft of this feature published `{action, ...}` directly with no `event` key) silently produces a useless `ws:undefined` DOM event instead of `ws:notification`. `data` is `{action: 'upserted', notification}` / `{action: 'deleted', id}` / `{action: 'unread_count', count}` (the last one fires after *any* mark-read, bulk or single, so every open tab/device for that user stays in sync). This project's WebSocket layer (`websocket/channels.js`) is a **generic** `subscribe(channel)/unsubscribe(channel)` relay already — a personal channel is just another channel name, no server-side change was needed to support it.

**Known, deliberate limitation**: the WebSocket server does not verify that a client subscribing to `notifications.users.{id}` actually *is* that user — any raw WS client could claim any id and receive that user's notifications. The app itself never exposes a way to pick an arbitrary id (it only ever subscribes using the current user's own id from `GET /api/auth/me`), so this isn't reachable through normal use, but it isn't a real access-control boundary either. Worth a dedicated hardening pass (e.g. a signed per-user channel token) if this ever needs to resist a deliberate attacker — not done as part of this feature.

**Testing gotcha hit while writing `NotificationTest.php`**: switching `actingAs($userA)` → real HTTP call → `actingAs($userB)` → real HTTP call **within the same test method** silently keeps resolving `$request->user()` as `$userA` for the second call, because the session/`sanctum` guard instance is memoized across the two simulated requests and `actingAs()` alone doesn't reset it. Call `$this->app['auth']->forgetGuards();` between the two `actingAs()` calls to force it to re-resolve. This hadn't come up before this feature because no earlier test switched between two different real, authenticated users within one test method (reaction-toggle tests always reused the same `$reactor` for both calls). Needed anywhere a test asserts "user B was notified/affected by user A's action."

### Product reviews API (2026-07-04)

First real usage of the `reviews` structure — product reviews, auth-gated writes, one review per user per product, and **every mutation reaches the browser exclusively over WebSocket** — the initial list is a plain paginated REST GET, fired once when the product page's Reviews tab is opened, not kept live by polling. **One level of reply threading is used (`parent_id`)** — any authenticated user can reply to any root review (not just a seller/admin), shown behind a "View N replies" expander. Replies go through the exact same four write endpoints as root reviews (`POST`/`PUT`/`DELETE`/`react`, differentiated only by `parent_id`) — there is no separate reply-only endpoint.

**`replied_to_comment_id` (2026-07-05)** — lets a reply address a *specific other reply* within the same thread (matching `srelon/demo-news`'s "reply to a reply" behavior) without adding a second level of nesting — replies stay flat under one root, this column just tags which one you're responding to. `ReviewRequest` validates it: the target must itself be a reply (`whereNotNull('parent_id')`) whose `parent_id` matches the request's own `parent_id` (same thread; rejects cross-thread ids and rejects targeting the root itself — the root already has its own plain reply path with no target). `formatReview()` exposes `replied_to_comment_id` + a `replied_to: {id, user: {name}}|null` convenience object (eager-loaded via `repliedTo.user`, no N+1). **Notification targeting**: `ReviewService::create()` resolves who gets the `reply` notification as `$replied_to_comment_id ?? $parent_id` — addressing a specific reply notifies *that reply's* author, not the root's, matching demo-news's own `$notify_comment_id = $request->input('replied_to_comment_id') ?? $request->input('parent_id')` fallback exactly.

**`GET /api/products/{slug}/reviews`** *(`ReviewController@index` → `App\Services\ReviewService`)* — public, no auth required. Response `{items: {data, pagination}, viewer_review, rating_breakdown}`:
- `items.data` — paginated (10 per page), root reviews only (`whereNull('parent_id')`), newest first, via `formatReview()`: `{id, parent_id, user: {name, avatar}, rating, body, created_at, can_edit, can_delete, likes_count, dislikes_count, my_reaction, replies_count, replies}`. `can_edit`/`can_delete`/`my_reaction` are computed against the requester (all `false`/`null` for a guest) — the frontend never re-derives the 24h edit-window rule itself, it just reads `can_edit`. **For an authenticated requester, their own review is excluded from `items.data`** (`ReviewService::getPaginated()` adds `->where('user_id', '!=', $viewer->id)` when a viewer is present) — the product page shows a caller's own review only via the separate `viewer_review` field (on the "write a review" side), never duplicated in the list itself.
- `replies` — each root review's replies (`parent_id = review.id`), oldest-first, each formatted with the *same* `formatReview()` shape (so a reply carries a `rating` too, but it's `null` and the frontend hides the stars for replies — "same card, minus the rating"). Replies are one level deep only: a reply's own `replies` is always `[]`/`replies_count` `0` (`formatReview` only expands `replies` for a root, `parent_id === null`, guarding against recursion). Eager-loaded via `->with(['replies' => fn ($q) => $q->oldest()->with(['user', 'likes'])])`, so no N+1. `viewer_review` carries its `replies` too (an admin can reply to the caller's own review).
- `viewer_review` — the current user's own review (any page, not just the first), or `null` if guest or hasn't reviewed yet — `ReviewService::getViewerReview()`. **Named for the requester, not `my_review`** — there's no "my" on the backend, only whichever user is making the request; the frontend variable is `viewer_review` too, matching `ReviewResource`'s existing `$viewer` naming for the same concept. This is what lets the product page show "your review" with Edit/Delete instead of a blank write form, even when that review isn't on page 1 of the list.
- `rating_breakdown` — `{5: n, 4: n, 3: n, 2: n, 1: n}`, count of root reviews at each star value across the *entire* product (not just the current page), via `ReviewService::getRatingBreakdown()` (`groupBy('rating')`, zero-filled for stars with no reviews). Powers the summary bar chart on the product page; the frontend derives each bar's percentage itself (`count / sum(all counts) * 100`), nothing pre-computed server-side beyond the raw counts.

**`body` is sanitized HTML, not plain text** (2026-07-04, once the frontend's review form gained bold/italic/underline/strikethrough via a `contenteditable` editor, mirroring `srelon/demo-news`'s `CommentForm.vue` — `document.execCommand()`-based, not markdown) — `ReviewService::sanitizeBody()` runs on every create/update, allowlisting only `<b><i><u><s><strong><em><br>` via `strip_tags()` and then stripping **all attributes** even off the allowed tags (`preg_replace('/<(b|i|u|s|strong|em|br)\b[^>]*>/i', '<$1>', ...)`) — plain `strip_tags($body, $allowed)` alone is not enough, since it would leave something like `<b onmouseover="...">` completely intact (the tag is allowed, `strip_tags` never touches attributes). This is a real stored-XSS surface once `review.body` is rendered with `v-html` on the frontend (necessary now that it's real HTML, not text) — sanitizing on the backend, at the actual trust boundary, is what makes that `v-html` safe, not a frontend-side precaution. A disallowed tag's own *text content* (not its markup) is intentionally left behind as inert plain text (`strip_tags`'s normal behavior) — e.g. a pasted `<script>alert(1)</script>` survives as the literal visible text `alert(1)`, which cannot execute; this is a minor content-quality wrinkle, not a security gap, and not worth a heavier HTML-parsing sanitizer for what this project needs. `ReviewRequest`'s `body` rule validates the **stripped-of-tags** text length (`mb_strlen(trim(strip_tags($value)))` — between 3 and 1000 characters), not the raw HTML length — otherwise `<b></b><br>` (no real content) would pass a naive `min:3` check, and the 1000-char cap counts visible text so formatting markup doesn't eat into the limit. The frontend's `ReviewForm.vue` counter mirrors this exact 1000 limit against `textContent`.

**`POST /api/products/{slug}/reviews`** *(`auth:sanctum`)* — `{rating: 1-5, body}` for a root review, or `{parent_id, body}` for a reply (`ReviewRequest` — one shared Form Request for create and update, per this project's convention, not two near-identical classes, and shared between root/reply too rather than a second Request class). `rating` is required only when `parent_id` is absent; a reply is always stored with `rating: null`. `parent_id` (when present) is validated against `$product->reviews()->whereNull('parent_id')->where('id', $parent_id)->exists()` — must be a root review belonging to *this* product, rejecting both cross-product ids and replying-to-a-reply (`422` either way, keeps threading exactly one level deep). Rejects with `403` if `ReviewService::hasReview()` is already true for this user+product **and `parent_id` is absent** — the "one review per product" rule only applies to root reviews; a user keeps posting replies freely even after (or before) writing their own root review.

**`PUT /api/products/{slug}/reviews/{review}`** *(`auth:sanctum`, same `ReviewRequest`)* — works on a reply id too. `403` unless `Review::canEditBy($user)` — owner **and** `created_at` is less than 24 hours old (`$review->created_at->gt(now()->subDay())`), matching `srelon/demo-news`'s comment edit-window exactly. Whether `rating` is required is decided by looking up the *existing* review's own `parent_id` (`Review::whereKey($id)->whereNotNull('parent_id')->exists()`), since the client doesn't resend `parent_id` on an edit.

**`DELETE /api/products/{slug}/reviews/{review}`** *(`auth:sanctum`)* — works on a reply id too; soft-deletes (the table already has `SoftDeletes`); `403` for a non-owner. No time limit on deleting your own review/reply (only editing has the 24h window).

**`POST /api/products/{slug}/reviews/{review}/react`** *(`auth:sanctum`)* — works on a reply id too. `{type: 'like'|'dislike'}` (`ReactReviewRequest`). `ReviewService::toggleReaction()` reuses `review_likes.opp_type` (`0` cancelled / `1` dislike / `2` like) exactly like `products_favorites.status`'s toggle pattern elsewhere in this schema — clicking the same reaction again cancels it (`opp_type → 0`), clicking the other reaction switches it, there's no separate "remove reaction" endpoint.

**`POST /api/products/{slug}/reviews/{review}/report`** *(`auth:sanctum`, 2026-07-06)* — works on a reply id too. `{reason?: string}` (`ReportReviewRequest` — `reason` is `nullable`, not validated against a fixed enum server-side; the frontend's dropdown is what curates the actual reason list, matching `srelon/demo-news`'s own `ReportCommentRequest`). `ReviewService::report()` is a plain `ReviewReport::updateOrCreate(['review_id', 'user_id'], ['reason'])` — a second report from the same user on the same review **updates** the stored reason rather than creating a duplicate row, backed by the table's own `unique(review_id, user_id)`. Response is just `{reported: true}`; no moderation/admin surface reads this table yet (see `backend/docs/database.md`'s "Not built yet" list in `CLAUDE.md`'s companion status memory). The frontend never persists "did I already report this" across a reload — `ReviewItem.vue`'s `reported` flag is session-local only (matching demo-news' own approach), not a `ReviewResource` field, so re-opening the page shows "Report" again even though re-submitting is harmless (`updateOrCreate`).

**`ReviewController::resolveReview()` has no `whereNull('parent_id')` filter** — deliberately, so `update`/`destroy`/`react`/`report` resolve a reply id just as well as a root id. Only `getPaginated()`/`getPaginated()`'s sibling read-path queries keep that filter (they specifically mean "root reviews only").

**These four write endpoints are the first real use of `auth:sanctum` middleware in this project** — the `auth/*` endpoints themselves deliberately avoid it (see § Auth: login/register need to behave correctly regardless of current session state), but a genuinely protected write action is exactly what the middleware is for, and it's safe now that `SANCTUM_STATEFUL_DOMAINS`/CSRF are confirmed working end-to-end (see § Auth for the bug history).

**`products.rating_avg`/`reviews_count` are recalculated on every create/update/delete** (`ReviewService::recalculateRating()` — `avg('rating')`/`count()` over the product's non-deleted **root** reviews, `whereNull('parent_id')`, so replies never inflate the count or skew the average) — these columns are already displayed everywhere a product card renders (listing, bestsellers, the product page's own star rating), so without this the reviews feature would be visually disconnected from the rest of the site.

**Real-time transport** — `ReviewService::publish(Product $product, string $event, array $data)` does `Redis::publish("reviews.products.{$product->slug}", json_encode(['event' => $event, 'data' => [...]]))`. Channel is keyed by **slug**, not the numeric product id, so nothing new needed exposing on `GET /api/products/{slug}` just for this. Every payload also carries a `product: {rating, reviews_count}` snapshot, so the frontend can patch the product page's header rating/tab count live without a second request. Events: `review.created`, `review.updated` (full `formatReview()` payload, including `parent_id`), `review.deleted` (`{id, parent_id}`), `review.liked` (`{review_id, parent_id, likes_count, dislikes_count, user_id, reaction}` — no full review object, keeps the payload small; every subscribed client, including the one who reacted, gets the same broadcast and diffs `user_id` against their own id to know whether to update their own "my reaction" state). **Every event carries `parent_id`** (`null` for a root review/reply-less event) specifically so the frontend can route a reply's create/update/delete/like into the right root review's `.replies` array instead of the top-level list — see `ReviewsPanel.vue`'s `find_review()` helper.

**Real bug hit and fixed while verifying this end-to-end (2026-07-04), not caught by any Pest test**: `Redis::publish()` silently never reached the websocket process. `config/database.php`'s redis `'options'` block sets a global key `prefix` (`{app-name}-database-`, used so cache/queue keys can't collide if this Redis instance is ever shared with another app) — but Predis's `KeyPrefixProcessor` applies that prefix to **every** command's first argument indiscriminately, including `PUBLISH`'s channel name, which isn't a "key" in any meaningful sense. So `Redis::publish('reviews.products.astral-journey', ...)` actually published to `laravel-database-reviews.products.astral-journey` on the wire — confirmed with `redis-cli monitor` while `websocket/channels.js` was subscribed to the unprefixed name, watching the publish arrive on a channel nobody was listening to. Pest's `Redis::spy()`/`shouldHaveReceived('publish')` tests all passed regardless, since they assert against the **call**, not what Predis does to the channel argument afterward — this class of bug is structurally invisible to a mocked-Redis test and only surfaces against a real Redis + real subscriber. Fixed by adding `'options' => ['prefix' => '']` to the `default` connection specifically (the one `Redis::publish()` uses with no explicit connection argument) — safe because nothing else in this app uses the `default` redis connection: caching goes through the separate `cache` connection (`REDIS_CACHE_DB`), and the queue driver is `database`, not `redis`. Re-verified with `redis-cli monitor` showing the bare channel name, and a real WebSocket client receiving the relayed message.

`websocket/server.js` is a from-scratch build for this feature (previously just logged incoming messages, Redis was connected but nothing subscribed to it): `websocket/channels.js` is one **generic** relay (`Map<channel, Set<ws>>`, subscribe/unsubscribe/relay) rather than a dedicated file per domain — there's only one real-time domain (reviews) right now, so a `demo-news`-style `article.js`/`comments.js`/`notification.js` split per domain would be premature. The browser side (`stores/websocket.ts`) is equally generic — `subscribe(channel)`/`unsubscribe(channel)`, re-dispatches every incoming message as a `window.dispatchEvent(new CustomEvent(\`ws:${event}\`))`, so the next real-time feature reuses the same connection instead of opening a second one.

## Cart / Favorites

**carts** — `user_id (unique)`, `status`. One cart per user.
**cart_items** — `cart_id → carts, product_id → products, quantity, status`.

Guest carts are **not stored in the DB** — client-side only (Pinia store + localStorage). Only an authenticated user's cart is persisted (so it syncs across devices).

**products_favorites** *(model `ProductsFavorite`, table renamed from `favorites`)* — `user_id → users, product_id → products, status`, unique(`user_id, product_id`). Clicking "favorite" again toggles `status` (0/1) instead of deleting the row.

## Delivery / Payment

**delivery_services** — carrier directory (Nova Poshta, self-pickup, etc.): `name, key (unique — for API lookups), status, price (rough estimate, informational only)`. Self-pickup is just a row here, not a `null` sentinel.

**delivery_branches** — actual branches/pickup points, synced from a carrier API: `delivery_id → delivery_services, city, branch, status, hash (unique — dedupes API data)`.

**payments** — payment method directory: `name, key, status`. Extensible for future payment gateways.

## Orders

**order_contacts** — `first_name, last_name, phone, email`. Reused across a customer's orders instead of duplicating the fields directly on `orders`.

**orders** — `public_id (unique — used in the order URL/status page instead of the real id), user_id (nullable — guest checkout), contact_id → order_contacts, delivery_id → delivery_services (required), delivery_branch_id → delivery_branches (nullable — not needed for self-pickup), payment_id → payments, status, paid_amount (nullable — a separate lump-sum amount for card payment of the whole order), txid (unique, auto-generated), tracking_number (nullable)`.

`public_id` and `txid` are **auto-generated** in `Order::booted()` (`static::creating`) — never set them manually on create. `users.public_id` (added 2026-07-05, `add_public_id_to_users_table` migration) is generated in `User::booted()` too, but as a **random 8-digit numeric string** (`random_int(10000000, 99999999)`, collision-checked against the table), not a ULID — deliberately short/typeable (a user-facing account number), unlike `orders.public_id`/`txid` which stay ULID/UUID since nobody needs to read those out loud.

**`users.id` (the raw auto-increment) is never sent to the frontend — `public_id` is the only user identifier that leaves the backend** (2026-07-06). Unlike products (whose numeric id was never exposed anywhere either, but there's no per-user enumeration concern there), a raw sequential user id would let anyone estimate signup volume/growth or probe for valid ids — the same reasoning `orders.public_id` already existed for. This touches more than just the profile response:
- `UserResource` (`/api/auth/profile`, `login`, `register`) returns `public_id`, not `id`.
- `NotificationService::publish()` builds the Redis channel as `notifications.users.{$user->public_id}`, not `.{$user->id}` — `App.vue`'s websocket subscribe/unsubscribe use `user.public_id` to match. `deleteReaction()` takes a `User $user` (not a raw `int $user_id`) specifically so it has `->public_id` available to publish with.
- `ReviewService::toggleReaction()`'s broadcast payload (the `review.liked` event on the product's review channel) carries `'public_id' => $user->public_id`, not `user_id` — `ReviewsPanel.vue`'s `on_review_liked` compares `data.public_id === auth_store.user?.public_id` to detect "did I just react" without a refetch.
- DB foreign keys (`user_notifications.user_id`, `review_likes.user_id`, etc.) are untouched — this is purely about what crosses the wire to the client, not the schema.

**order_items** — `order_id → orders, product_id → products, product_stock_id → product_stocks, price (snapshot at order time), quantity (ordered), fact_quantity (actually shipped), paid_amount (actually paid for this line), status`. Title/author/image are not duplicated — pulled through `product_id`.

`orders.status` and `order_items.status` are **independent**: one order can have some items cancelled and others delivered. Planned admin flow (not implemented yet): set `order_items.status` first, then setting `orders.status` back-fills any untouched items.

## Navigation

**menus** *(model `Menu`, no `status`, no `softDeletes` — unlike the rest of this doc's tables)* — `name, route (nullable), parent_id, type (link = external URL / route = a Vue Router route name from frontend/src/routes/router.ts, e.g. "products", "about" — not a path, and not a Laravel route), params (json, nullable — route params for dynamic segments, e.g. {"slug": "..."} for the "product"/"post" routes, only relevant when type=route), sort_order, location (header/footer)`.

The frontend resolves a `type=route` item as `:to="{ name: menu.route, params: menu.params }"` (vue-router's named-route object form), not as a raw path string.

In the admin (`MenuTree::routeSlugModels()`), the `product`/`post` routes get a searchable "Target" select instead of a free-text params box — it queries `Product`/`NewsPost` by `title` (last 10 by id, filtered as you type) and writes the picked record's `slug` into `params.slug`, so an editor never hand-types a slug that could drift from the real record.

`MenuSeeder` seeds the 6 top-level `header` items straight from `AppHeader.vue`'s `nav_links` (Home/Products/Authors/About Us/News/Contact Us) — the "Categories" mega-menu in the same header is driven by `products_categories`, not `menus`, so it isn't duplicated here. `footer` isn't seeded yet — its layout isn't finalized in the frontend.

Powers a WordPress-style drag-and-drop menu editor at `/admin/menu-tree` (`App\Filament\Pages\MenuTree`, gated by the `menus` access key like every other resource), built on `solution-forest/filament-tree` rather than a hand-rolled tree — see `config/filament-tree.php` for the column-name mapping (`order → sort_order`, `title → name`, `parent → parent_id`).

`parent_id` is **not** a nullable self-referencing FK like elsewhere in this schema — the package requires `-1` as the sentinel for a root/top-level item (`integer default(-1)`, no FK constraint, since `-1` never matches a real row). `parent_id` being a real menu id means the item renders inside that parent's dropdown. `$maxDepth = 2` on the page caps nesting at one dropdown level (top-level items + their direct children) — matches how the header/footer nav actually renders, not an arbitrary limit.

Deleting a parent cascades to its children (handled by the package's model trait, not application code).

**contact_info** *(model `ContactInfo`, table `contact_info` — explicitly set via `$table`, not the Eloquent-guessed `contact_infos`, and deliberately not named `contacts` to avoid confusion with `contact_messages`, the unrelated contact-form-submissions table)* — `name (label, e.g. "Phone"), content (the value, e.g. "578-393-4937"), icon (plain text, an inline SVG path string like "M7.5 0A5.5...", not JSON — unlike every other icon/image column in this schema, because that's what `ContactPage.vue` actually hands the `<path d>` attribute, not an uploaded file), key (unique — lookup key, e.g. "phone"/"email"/"address"/"working_hours"), status, sort_order`. A directory table like `delivery_services`/`payments`. `ContactInfoSeeder` seeds the 4 rows straight from `ContactPage.vue`'s `contact_info` array — the `href` (`mailto:`/`tel:`) shown there isn't a column, the frontend derives it from `key` (`email`/`phone`) instead of storing it.

**faqs** *(model `Faq`)* — `title, content (text — answers run to a paragraph, same as `products.description`), type (plain string, not an enum — which page/section it belongs to, e.g. "contact" for `ContactPage.vue`'s FAQ block; add new type values freely as more pages get FAQs), status, sort_order`. `FaqSeeder` seeds the 6 `type=contact` rows straight from `ContactPage.vue`'s `faq` array (`question`/`answer` → `title`/`content`).

## SEO

**seo_meta** — one shared table for SEO fields instead of duplicating `seo_title`/`seo_description`/`seo_keywords` on every content table: `type, record_id, seo_title, seo_description, seo_keywords`, unique(`type, record_id`).

`type` stores a short alias (the target's table name — `products`, `products_categories`, `news_posts`, `pages`), not a PHP class name. This is wired through Eloquent's morph map (`Relation::enforceMorphMap` in `AppServiceProvider::boot()`), so `record_id`/`type` still work as a normal polymorphic relation (`Product::seo()`, `ProductsCategory::seo()`, `NewsPost::seo()`, `Page::seo()` are all `morphOne(SeoMeta::class, 'seo', 'type', 'record_id')`) while keeping the column human-readable.

**`pages`** *(model `Page`)* — `slug (unique — home/products/authors/news/contact/about/cart), title, content (nullable text), image (nullable JSON, same {"original": "..."} shape as every other image column), excerpt, status, sort_order`. This is what makes every static/listing page (the ones with no natural content record of their own — Home, the Products/Authors/News *listings* as opposed to a single product/post, Contact, About, Cart) work with the exact same `seo_meta` polymorphic mechanism as `Product`/`NewsPost`/`ProductsCategory`, instead of a second special-cased SEO table or a type-sniffing branch somewhere. `PageService::getPage(string $slug)` looks up the row by `slug` (must be `status = 1`), returning `{title, content, excerpt, image, seo: {title, description, keywords}}` — the nested `seo` prefers the linked `seo_meta` row's `seo_title`/`seo_description`/`seo_keywords`, falling back to the page's own `title`/`excerpt` when no `seo_meta` row exists yet (so a page is never left with a blank SEO block just because nobody has filled in the dedicated fields). Returns `null` for an unknown or inactive slug — callers treat that as "nothing to show", not an error.

**Every static/listing page is grouped behind one `StaticController`** (`Route::prefix('pages')->controller(StaticController::class)->group(...)`, same "group routes by resource" convention as `Products`/`Authors`/`News`), with one method per page that needs extra composed data plus a catch-all fallback:

```php
Route::prefix('pages')->controller(StaticController::class)->group(function () {
    Route::get('home', 'home');
    Route::get('contact', 'contact');
    Route::get('about', 'about');
    Route::get('{slug}', 'show');
});
```

`{slug}` is registered **last** — Laravel matches routes in registration order, so `home`/`contact`/`about` resolve to their own dedicated method first and only anything else falls through to the wildcard. Each of `home()`/`contact()`/`about()` just calls its own existing Service (`HomeService::getHome()`, `ContactService::getContact()`, `AboutService::getAbout()` — unchanged, all business logic stays there per the "no logic in controllers" rule) and each of those already folds `'page' => $this->pageService->getPage('<own slug>')` into its own response, so `data.page.title`/`data.page.excerpt`/`data.page.seo.*` sit alongside that page's own other data (`bestsellers`/`faqs`/`team`). `show(string $slug)` handles everything else (currently just `cart`, and any future static page added later) with the bare `getPage()` result *as* the whole response — `data.title`/`data.seo.*` directly, no extra nesting, since there's nothing else to nest it alongside. **Adding a new page that needs more than plain page content means adding one more explicit route + controller method here, not a new controller/route file.**

`Home.vue`'s H1/description (`HeroSection` `title`/`description` props) and `AboutPage.vue`'s quote/intro paragraph/`PageBanner` title are sourced from `page.title`/`page.excerpt`/`page.content` — the first real frontend consumers of these fields beyond the SEO fallback. `image` still isn't consumed by any page yet.

**`team_members`** *(model `TeamMember`)* — `name, role, initials, color, bio, status, sort_order`. Backs the About page's "Meet The People Behind Our Bookstore" section (`AboutPage.vue`'s `team__grid`, previously a hardcoded array) — a flat table, not polymorphic, since a team member isn't a "page" and doesn't need SEO of its own. `TeamService::getTeamMembers()` returns active rows ordered by `sort_order` as `{name, role, initials, color, bio}`.

**`perks`** *(model `Perk`)* — `title, description, icon, status, sort_order` (`icon` is a plain inline SVG path string, same convention as `contact_info.icon` — not JSON). Backs the About page's bottom perks strip (`AboutPage.vue`'s `about-perks__grid` — Free Delivery / 24/7 Support / Easy Returns / Secure Checkout, previously a hardcoded array) — flat, not polymorphic, same reasoning as `team_members`. `AboutService::getPerks()` (a protected method on `AboutService` itself, not a separate `PerkService` — same "simple flat query doesn't need its own service class" precedent as `ContactService::getFaqs()`) returns active rows ordered by `sort_order`, mapping the `description` column to a `desc` key in the response (`{title, desc, icon}`) to match the frontend's existing prop name.

**`GET /api/pages/about`** (via `AboutService::getAbout()`) — response `{team, perks, page}`. `AboutService` composes `TeamService::getTeamMembers()` + its own `getPerks()` + `PageService::getPage('about')`, same pattern as `HomeService` composing `ProductService`/`BlogService`/`PageService`. **Cached** (general, non-personalized, same-for-every-visitor data) — `Cache::tags([CacheService::TAG_ABOUT])->remember(...)`, `TTL_ABOUT = 900s`; `TeamMember`/`Perk::booted()` call `CacheService::flushOnTeamWrite()`/`flushOnPerkWrite()` on save/delete, and `flushOnPageWrite()` (already shared by `Page`/`SeoMeta`) still flushes `TAG_ABOUT` too.

## Auth

Customer-facing auth (the `users` guard/table) uses **Sanctum SPA (cookie) authentication** — matches the frontend's `axios.ts` (`withCredentials: true`). Admin panel auth (the `admins` guard) is untouched and stays separate.

Infra:
- `routes/api.php` registered in `bootstrap/app.php`, with `$middleware->statefulApi()` enabled
- `config/sanctum.php` — `guard => ['web']` (the `web` guard already points at the `users` provider)
- `config/cors.php` — `supports_credentials: true`, `allowed_origins` derived from `SANCTUM_STATEFUL_DOMAINS` (scheme added automatically: `http://` in local, `https://` otherwise)
- `.env` — `SANCTUM_STATEFUL_DOMAINS` must be bare `host:port` entries (no scheme) — Sanctum matches against the request's Origin/Referer host directly; CORS derives its own scheme-prefixed origins from the same variable. **This was actually broken until 2026-07-04** — `.env` had scheme-prefixed values (`"http://127.0.0.1:8000,..."`), which this doc already said not to do, but nothing had exercised real session-cookie auth yet to surface it. `Laravel\Sanctum\Http\Middleware\EnsureFrontendRequestsAreStateful::fromFrontend()` strips `http(s)://` off the *incoming* request's Referer/Origin before comparing, but never strips it off the *configured* `sanctum.stateful` patterns — so a scheme-prefixed config value can never match, meaning the `web` session middleware group never actually got attached to any request, silently breaking cookie-session auth entirely (not just a test artifact — the same mismatch would happen against a real browser request from the real Vite dev server). Fixed by stripping the `http://` prefixes from `.env`'s `SANCTUM_STATEFUL_DOMAINS`; caught by `AuthTest::test_logout_clears_the_session` failing with "Session store not set on request."

**`GET /api/csrf-cookie`** *(`Laravel\Sanctum\Http\Controllers\CsrfCookieController@show`, registered directly, 2026-07-04)* — Sanctum's own default route is `GET /sanctum/csrf-cookie`, **not reachable in this project**: `filament_nginx`'s config only proxies `/api/*` (and `/admin`, `/livewire*`, `/storage/`) to PHP-FPM — `location / { try_files $uri @vue; }` sends everything else to the built frontend's `dist/index.html` SPA fallback, so a request to `/sanctum/csrf-cookie` silently returns the SPA shell (200, `text/html`, no `Set-Cookie`) instead of ever reaching Laravel. Re-registering the same `CsrfCookieController` under `/api/csrf-cookie` sidesteps this without touching the nginx config. `plugins/axios.ts`'s request interceptor calls it once (before the first non-`GET` request, if no `XSRF-TOKEN` cookie exists yet) — same "check-then-fetch" shape as the equivalent interceptor in `srelon/demo-news`'s `axios.ts`, which independently arrived at the same `/api/csrf-cookie` path for what's presumably the same reason.

**`GET|POST /api/auth/*`** *(2026-07-04, controllers split 2026-07-05 to match Laravel's standard per-action Auth controller layout — see `srelon/demo-news`)* — six endpoints under `Route::prefix('auth')->group(...)`, no route-level `guest`/`auth` middleware (every action is idempotent regardless of current session state, so the guard-alias complexity wasn't worth it for this pass). Split across four controllers, all thin wrappers over `App\Services\AuthService`:
- `POST auth/register` / `POST auth/login` / `POST auth/logout` — `App\Http\Controllers\Auth\AuthController` (kept as one controller for these three, not split further per-action — matches `demo-news`'s own `Auth/AuthController`, not vanilla Breeze's `RegisteredUserController`/`AuthenticatedSessionController` split).
  - `register` — `{name, email, password, password_confirmation}` (`RegisterRequest`: `Rule::unique('users','email')`, `Password::defaults()`). Creates the user, logs them in immediately (`Auth::login()`) — no email verification step, out of scope for now. Response `{user: {id, name, email, avatar}}`.
  - `login` — `{email, password}`. Controller just calls `LoginRequest::authenticate()` (matches `srelon/demo-news`'s `Auth\LoginRequest` / Breeze's stock shape) — the request itself owns `Auth::attempt()`, throttling, and the failure response, not the controller. 5 failed attempts per `email|ip` throttle key (`RateLimiter`, `Illuminate\Auth\Events\Lockout` fired on trip) locks out further attempts for 60s with `auth.throttle`'s translated message; a failed attempt within the limit responds `422 {errors: {email: ['These credentials do not match our records.']}}` (`auth.failed`) — no user enumeration hardening beyond that (matches this project's existing directness, e.g. `NewsletterSubscribeRequest`'s specific "already subscribed" message). Both `auth.failed`/`auth.throttle` resolve from Laravel's built-in translation fallback without needing a published `lang/en/auth.php`.
  - `logout` — `Auth::guard('web')->logout()` + `$request->session()->invalidate()`/`regenerateToken()`.
- `POST auth/forgot-password` — `App\Http\Controllers\Auth\PasswordResetLinkController@store` (Breeze-standard name/method for this one action). `{email}` (`ForgotPasswordRequest`, no `exists:users` check, same reasoning as `login`). `Password::sendResetLink()`; non-`RESET_LINK_SENT` statuses (e.g. unknown email) respond as a `422` error with Laravel's own translated status string.
- `POST auth/reset-password` — `App\Http\Controllers\Auth\NewPasswordController@store` (Breeze-standard name/method). `{token, email, password, password_confirmation}` (`ResetPasswordRequest`). `Password::reset()`; does **not** auto-login the user afterward — matches Laravel's own default broker behavior (reset only resets the password), the user logs in separately with the new password.
- `GET auth/profile` — `App\Http\Controllers\ProfileController@show` (a plain top-level controller, not under `Auth\` — mirrors `demo-news`'s `Site\ProfileController`, since "fetch the current user" is a profile concern, not an authentication action). **Deliberately has no auth middleware and never errors**, response is always `200 {user: {...} | null}`. The frontend calls this once on every app boot (`stores/auth.ts`'s `fetch_user()`, alongside `useLayoutStore().fetch_layout()` in `App.vue`'s `onMounted`) to silently restore a session across page reloads; this project's global axios interceptor (`plugins/axios.ts`) shows an error toast on every failed request, so a `401` here would toast "Something went wrong" for every anonymous visitor on every page load. Returning `200`/`null` avoids that without adding a per-request opt-out to the shared interceptor. Named `profile`, not `me`, to leave room for a real profile-editing endpoint on the same controller later without a rename.
- `App\Models\User` needed **no changes** — it already extends `Illuminate\Foundation\Auth\User`, which itself already `use`s `CanResetPassword`/`Notifiable`/`MustVerifyEmail`, so the reset-password broker worked out of the box.
- `ResetPassword::createUrlUsing()` (`AppServiceProvider::boot()`) points the reset-link email at the frontend, not a nonexistent Blade route: `{FRONTEND_URL}/reset-password?token={token}&email={email}`. New `config('app.frontend_url')` (`FRONTEND_URL` env var, default `http://localhost:5173`). The frontend's `reset-password` route reads `token`/`email` from the query string, primes `stores/auth.ts`'s `reset_credentials` + opens the auth modal on the `reset` tab, then redirects to `home` — same `beforeEnter`-calls-a-Pinia-store shape as the existing `cart` route, not a full page.
- **Not cached** — per-request, personalized by definition.

## API response format

Ported from the same source project as the reviews structure: `App\Traits\RespondTrait` (used by the base `Controller`), giving every controller `respondWithJson($content, $status = 200)` → `{data, status}`, `respondWithError($message, $code = 400)` → `{status, errors}`, and `paginationMeta($paginated)` for a compact pagination envelope (`current_page, last_page, total, prev_page_url, next_page_url` — the latter two are just `'prev'`/`'next'`/`null` flags, not real URLs).

**Every paginated listing endpoint (`GET /api/products`/`/authors`/`/news`) names its paginated array `items`, never a resource-specific name (`products`/`authors`/`posts`)** — `respondWithJson()` checks specifically for an `items` key holding a `LengthAwarePaginator` and, if found, replaces it with `{data, pagination}` (via `paginationMeta()`), so the paginated rows and their pagination metadata are nested together under `items` instead of `items`/`meta` being two unrelated siblings. A listing controller just does `respondWithJson(['items' => $paginated, 'filter_groups' => [...]])` — pass the paginator straight through under the fixed `items` key, no manual `->items()`/`paginationMeta()` calls. One response can only ever have one paginated list in it, so this is a single known key to check, not a loop over the whole array. `ProductController`/`AuthorController`/`NewsController` all rely on this instead of each calling `->items()`/`paginationMeta()` by hand.

**Form Request validation failures also match this envelope** — `bootstrap/app.php` renders `ValidationException` on `api/*` routes as `{status: 422, errors: $e->errors()}` (a `{field: [messages]}` map) instead of Laravel's default `{message, errors}` shape, so the frontend's error handling doesn't need a special case for validation vs. any other `respondWithError()` failure.

**`GET /api/layout`** *(`LayoutController` → `App\Services\LayoutService`, first real endpoint, fetched once on app load by the frontend's `useLayoutStore().fetch_layout()`)* — `{categories, menu, contacts, best_books}`:
- `categories` — delegated to `App\Services\ProductService::getCategories()` (moved out of `LayoutService`, same "other pages will need this too" reasoning as `bestsellers`/`best_rated`/`blog`) — active `products_categories`, `icon`/`image` are both raw relative storage paths (e.g. `"products_categories/category-icon-1.svg"`, not a full URL — the frontend's `to_storage_url()` helper in `stores/layout.ts` prepends `VITE_APP_URL`/`storage/`), `count` is `products()->count()`, not a stored column. `image` drives `AppHeader.vue`'s mega-menu promo panel — it swaps to the hovered category's `image` (falls back to the first category when nothing's hovered).
- `menu` — `location=header` items only, root items (`parent_id = -1`) with one level of `children` nested inline (matches `MenuTree`'s `$maxDepth = 2`). Each item is `{id, name, type, route, params, children}` — a `route` item's `route` is a Vue Router name, resolved by the frontend as `{ name: route, params }`, not a path.
- `contacts` — active `contact_info`, ordered by `sort_order`. `icon` is the raw inline SVG path string (see § Navigation) — the frontend feeds it straight into a `<path d>`, no URL resolution needed (unlike `categories.icon`).
- `best_books` — `App\Services\ProductService::getBestsellers(5)`, the same query/shape `HomeService` uses for the Home page's bestsellers section, just a smaller limit. Added here because `Sidebar.vue`'s "Best Selling Books" block is shared by `NewsList.vue`/`AuthorList.vue` (and any future page using `Sidebar.vue`) — global/cross-page data belongs in `useLayoutStore()`, not duplicated as a hardcoded array in every page that renders the sidebar (see CLAUDE.md § Frontend "Pinia store" rule). Since this makes `best_books` depend on `products`/`product_stocks`/`products_authors`, `CacheService::flushOnProductWrite()` now flushes `TAG_LAYOUT` too, not just `TAG_HOME`.

**`POST /api/newsletter`** *(`NewsletterController` → `App\Services\NewsletterService`, validated by `NewsletterSubscribeRequest`)* — body `{email}`, creates a `newsletter_subscribers` row with `status = 1`. `email` must be unique (case handled by the DB's default collation, not application code) — a duplicate returns `422 {status: 422, errors: {email: ["This email is already subscribed."]}}`, which `components/ui/shop/NewsletterForm.vue` surfaces via `vue-toastification` (see CLAUDE.md § Frontend for the toast convention). No unsubscribe/resubscribe flow yet — a previously-unsubscribed email (`status = 0`) still collides with the unique check rather than being reactivated.

**`GET /api/pages/home`** *(`StaticController@home` → `App\Services\HomeService`, fetched once by the Home page)* — `{bestsellers, best_author, best_rated, blog}`:
- `bestsellers`/`best_rated`/`best_author` are delegated to `App\Services\ProductService` (`getBestsellers(int $limit = 8)`, `getBestRated(int $limit = 9)`, `getBestAuthor()`), not built inline in `HomeService` — these are generic product-listing queries, not Home-page-specific, so any future page needing "top N by rating"/"bestsellers"/"best author" reuses this same service rather than re-deriving the query. `bestsellers` is `ORDER BY bestseller DESC, rating_avg DESC LIMIT 8`. `bestseller` is deliberately left as the existing `0`/`1` flag (not converted to a weighted score) — decided back when the demo catalog only had 7 products and 2 flagged (see § Seed data for the later 40-product expansion, 8 flagged of 47 now) — a real weighted score would need actual sales-volume data this project doesn't have yet. `price` comes from `Product::activeStock`, `image` from the `Product::primaryImage` relation (`hasOne(ProductImage::class)->orderBy('sort_order')` — a `hasOne`, not a `hasMany` capped with `->limit(1)` in the eager-load closure, which would silently apply the limit to the *whole* batched query across every loaded product instead of one-per-product; `hasOne` doesn't have that bug since Laravel groups by parent key during hydration instead of at the SQL level). `best_author` is the `products_authors` row whose products have the highest `SUM(bestseller)` (tie-broken by `AVG(rating_avg)`), grouped straight off `products.author_id`. `photo` is `null` for every seeded author (see § Seed data) — the frontend needs a fallback image/avatar for this, there's no real photo data yet. `best_rated` is the same shape as `bestsellers`, `ORDER BY rating_avg DESC LIMIT 9`. Both are thin wrappers around a shared `topProducts(array $orderByDesc, int $limit)` (2026-07-03 — the only real difference between them was which columns to `orderByDesc()` and in what order) — `getBestsellers()` passes `['bestseller', 'rating_avg']`, `getBestRated()` passes `['rating_avg']`.
- `blog` — delegated to `App\Services\BlogService::getLatestPosts(int $limit = 7)`, same reasoning as `ProductService` — active `news_posts`, `ORDER BY published_at DESC`. Now also reused by the full News listing page, see `GET /api/news` below.

**`GET /api/products`** *(`ProductController` → `ProductFilterRequest` → `App\Services\ProductService::getFilteredList()`/`getFilterGroups()`, powers the Products listing page)* — query params `category[]`, `author[]`, `price_min`, `price_max`, `rating`, `status[]`, `sort_by`, `page`; response `{items: {data, pagination}, filter_groups, page}`:
- `items.data` — paginated (9 per page, Laravel's own `paginate()`, reads `page` from the query automatically), same shape as `HomeService`'s product cards (`ProductService::formatProduct()`). `items.pagination` is `paginationMeta()`'s envelope (`current_page, last_page, total, prev_page_url, next_page_url`). **All `Product::activeStock`-derived fields are grouped under one nested `stock` object** (2026-07-04) — `{price, before_price, id, quantity}` — rather than flattened onto the product card, since they're all read off the same relation and a consuming component (an "Add to Cart" control) needs them together anyway. `stock.quantity` is the *available* quantity (see § Stock availability for the exact reservation formula), not the raw `product_stocks.quantity` column, so a product with real stock but fully reserved by pending/shipped orders correctly shows `0` here. `stock.id` is `Product::activeStock->id`, meant for the frontend to pass back when adding to cart/placing an order (pins the line item to the exact batch its price/availability was read from, matching `order_items.product_stock_id`'s own purpose). `ProductService::formatStock(?ProductStock $stock, bool $includeAvailability = true)` is the one place that builds this object, shared by `formatProduct()` and `formatProductDetail()` — `price`/`before_price` are always present (needed for plain display everywhere, including pages with no cart action), while `id`/`quantity` are only added when `$includeAvailability` is true. `formatProduct(Product $product, bool $includeStock = true)` forwards its own flag through to `formatStock()` — every consumer that renders an "Add to Cart" action gets the full object (the product listing, `GET /api/home`'s `bestsellers`, `GET /api/products/{slug}`'s `related`, and `GET /api/products/{slug}` itself via `formatProductDetail()`), but `HomeService`'s `best_rated` (`ProductService::getBestRated()` → `topProducts(..., includeStock: false)`) gets `stock.price`/`stock.before_price` only — its cards (`RatedCard.vue`) show a price but have no cart action, so `stock.id`/`stock.quantity` would have nothing on the frontend to consume them. Every checkbox filter (`category`, `author`, `status`) matches by **display name**, not slug/id — `whereHas('category', fn ($q) => $q->whereIn('name', $filters['category']))` — this deliberately matches the existing convention everywhere else in the frontend (`AppHeader`'s mega-menu and `HeroSection`'s category cards already link via `query: { category: cat.name }`), not a shortcut. Multiple values within one checkbox group are OR'd (`whereIn`/`orWhereHas`); different groups are AND'd together.
- `status` values are the literal strings `"In Stock"` (`activeStock.quantity > 0`), `"On Sale"` (`activeStock.before_price` is not null), and `"Bestseller"` (`products.bestseller = 1`) — same name-matching convention as category/author, not a coded enum, so the frontend doesn't need a separate value↔label mapping. `BestsellersSection.vue`'s "View All" link points at `/products?status=Bestseller` so it lands on the same filter the section itself is ranked by.
- `sort_by` — `default` (by `id`), `popularity` (`bestseller DESC, rating_avg DESC`), `rating` (`rating_avg DESC`), `price_asc`/`price_desc` (ordered by a correlated subquery on `product_stocks.price` — Eloquent can't `orderBy()` across a relation directly, and joining would multiply rows for products with several stock batches, so this uses `Builder::orderBy($subquery)` instead, scoped to the same `status = 1` + `latest(sort_order)` active-stock rule as `Product::activeStock()`), `newest`/`oldest` (`published_at DESC`/`ASC` — not `created_at`, since `published_at` is the customer-facing "went live" date and is already indexed for this).
- `filter_groups` — same shape as `ProductSidebar.vue`'s old hardcoded `FilterConfig[]`, now server-built. `category`/`author`/`status` are **faceted**: each group's items/counts are computed against the *other* currently-active filters, excluding that group's own filter (`ProductService::applyFilters($query, $filters, except: [...])`). Selecting a category narrows the `author`/`status` groups (and their counts) down to what's actually reachable within that category, while the `category` group itself stays showing every category (so the user can switch categories rather than getting stuck once one is picked) — same reasoning applies to every other faceted group excluding itself. **`price`'s `min`/`max` are deliberately *not* faceted** — `priceFilterGroup()` always returns the real `MIN(price)`/`MAX(price)` across the *entire* active catalog, regardless of any other active filter, not a value that narrows as other filters change. This was tried the faceted way first and reverted (2026-07-03): a price range that shifts every time a category/author gets selected is unpredictable UX (the slider's own boundaries move under the user while they're using it) and was also the direct cause of a cascade of `PriceFilter.vue` bugs (creeping thumbs, both handles moving together, thumbs bunching up when the shifting bounds happened to collapse to a single price) that kept resurfacing no matter how the frontend tried to compensate for it — fixing it at the source (stop the bounds from moving) was simpler and more correct than chasing the frontend symptoms. **Not cached** — once category/author/status counts depend on the active filter combination, `filter_groups` has exactly the same "too many combinations for decent hit rate" problem as the product listing itself (see § Caching), so both are computed fresh per request; only `LayoutService`/`HomeService` stay cached, since those genuinely don't vary per request.
- **`category`/`author`/`status` items with a `count` of `0` are excluded — unless that item is itself currently selected.** No point offering a checkbox that can only ever return zero results, but a selected item that happens to combine with the *other* active filters into zero results must stay visible so the user can actually see and un-check it — hiding it would make an active filter impossible to remove from the UI. `categoryFilterGroup()`/`authorFilterGroup()` are both thin wrappers around a shared `checkboxFilterGroup(filters, model, title, queryKey, orderBy, scopedByStatus)` (2026-07-03 — the two were ~99% identical, merged once that became obvious) that queries the given model with `withCount(['products' => fn ($q) => ...])` (a correlated subquery scoped by the *other* active filters, matching `applyFilters($q, $filters, except: [...])`) rather than an `INNER JOIN` — a join would silently drop zero-count rows from the result set entirely, which is exactly wrong once a selected-but-zero-count item needs to still appear. The keep-it-visible exception is a plain `$item['count'] > 0 || in_array($item['name'], $selected, true)` check in PHP, not a SQL-level filter. **`scopedByStatus` exists because the two aren't fully identical**: `products_categories` has a `status` column (disabled categories excluded via `->where('status', 1)`), `products_authors` does not — passing this as a bool param rather than silently applying `where('status', 1)` unconditionally would have broken authors (no such column to filter on). That keep-it-visible-unless-zero check plus the `{title, type: 'checkbox', query_key, items}` envelope is itself shared a second level down, in `checkboxGroup(title, queryKey, items, selected)` — `checkboxFilterGroup()` maps its Eloquent results into plain `{name, count}` arrays first, and `statusFilterGroup()` builds its two-item `{name, count}` array by hand (via `filteredBaseQuery()` counts), but both then hand that plain array to the same `checkboxGroup()` for the filter+wrap step, rather than each re-implementing the "hide zero-count unless selected" rule and the response shape separately.
- **`category`/`author`/`status` accept three input shapes**: a bare string (`?category=Fantasy` — `AppHeader`'s mega-menu, `HeroSection`'s category cards, `ProductCard`'s in-card category badge all navigate this way), a **comma-separated string** (`?category=Fantasy,Cooking` — this is what `ProductSidebar.vue`'s multi-select checkboxes actually produce now), or a PHP-style bracket array (`?category[]=Fantasy&category[]=Cooking`, kept for backward compatibility/manual testing). `ProductFilterRequest::prepareForValidation()` normalizes all three into a plain array before the `'array'` rule runs — `explode(',', $value)` when the scalar contains a comma, `[$value]` otherwise. **Comma-separated, not repeated `category=A&category=B` keys, is the deliberate choice for multi-select** — Vue Router's own query stringifier serializes an array-valued `route.query` entry as repeated same-name keys (not PHP's `key[]=` bracket convention), which is fine for Vue Router's own parse/stringify round-trip but reads oddly in the address bar and doesn't match how the rest of this app's query params look; joining the selected values into one comma-separated string before writing to `route.query` keeps the URL a single `key=value` pair, matching every other query param here.
- **A `category`/`author`/`status` value that doesn't match anything real (a typo, hand-edited URL) is harmless server-side** — `whereIn('name', [...])` simply never matches it, no error, no effect on the other valid values in the same list. `price_min`/`price_max` are different: a non-numeric value there used to 422 the *entire* request (the `'numeric'` validation rule rejecting it outright), which meant `filter_groups` and `items` both failed to load from a single bad query param. `ProductFilterRequest::prepareForValidation()` now strips a non-numeric `price_min`/`price_max` from the request *before* validation runs (`$this->query->remove($key)` — note this is `$this->query`, not `$this->request`; for a GET request the query string lives in the `query` bag, `request` is the POST body bag, a distinction that silently no-ops if you remove from the wrong one), so it's treated exactly as if the param was never sent, matching the already-lenient behavior of the array filters instead of erroring.
- **`page` deliberately has no validation rule at all** (not even `'integer'`) — Laravel's own `AbstractPaginator::isValidPageNumber()` already does `filter_var($page, FILTER_VALIDATE_INT) !== false`, falling back to page 1 for anything invalid, before the query ever runs. Adding a `'page' => ['integer']` rule (tried briefly, then reverted the same session) just reintroduces the exact 422-on-garbage-input bug the `price_min`/`price_max` fix above exists to avoid — the framework already does the graceful-fallback job for free, no custom `prepareForValidation()` handling needed or wanted here.

**`GET /api/products/{slug}`** *(`ProductController@show` → `App\Services\ProductService::getBySlug()`/`formatProductDetail()`/`getRelatedProducts()`, powers the single product page)* — response is a flat product bundle (not the `{items, filter_groups, page}` listing shape) plus `related`: `{slug, title, author, category, rating, reviews_count, short_description, description, images, stock: {price, before_price, id, quantity}, seo, related}`. `stock` (via the shared `formatStock()`, see § API response format → `GET /api/products`) always includes the full `{price, before_price, id, quantity}` shape here — this is the page with the actual "Add to Cart" quantity stepper, so it needs the real cap:
- `getBySlug()` matches `status IN (1, 2)` — active and archived both resolve (archived is "reachable only via direct link, not searchable", see § Status field reference), anything else (`0`/`3`/`4`) 404s via `respondWithError('Product not found.', 404)`.
- `images` is every `product_images` row's `image.original` (not just `primaryImage`) — the single product page's gallery/thumb-slider needs the full set, unlike a product card which only shows one cover.
- `seo` is `Product::seo()` (not `pages`/`PageService` — a product isn't a `pages` row), falling back to `title`/`short_description` when no `seo_meta` row exists, same fallback shape as `PageService::getPage()`. Sits at the top level of `data` (not nested under a `page` key) since there's no separate page bundle here — matches `axios.ts`'s interceptor `data?.page?.seo ?? data?.seo` fallback.
- `related` — up to 4 other active products (`baseQuery()`, so `status = 1` only, unlike the show product itself which also allows archived) sharing the same `category_id`, excluding the product itself, formatted via the same `formatProduct()` the listing/home endpoints use.
- **Not cached** — same per-request-detail reasoning as `GET /api/authors`/`GET /api/news`; only bundle endpoints that are identical for every visitor (`layout`/`home`/`contact`/`about`) are cached.

**`GET /api/authors`** *(`AuthorController` → `AuthorFilterRequest` → `App\Services\AuthorService::getFilteredList()`, powers the Authors listing page)* — query params `sort_by`, `page`; response `{items: {data, pagination}, page}`:
- `items.data` — paginated (6 per page), `{slug, name, initials, color, bio, books, bestsellers}`. No filter_groups/facets like Products — this page only sorts, it doesn't filter. `initials` is derived server-side from `name` (first letter of the first two whitespace-separated words), `color` falls back to `#999999` when `avatar_color` is null, `bio` falls back to `''` when `content` is null — `products_authors` has neither an `initials` nor a guaranteed-non-null `content`/`avatar_color`, so the frontend doesn't need its own fallback/derivation logic. `books` is `products()->count()` via `withCount('products')`, `bestsellers` is `SUM(products.bestseller)` via `withSum('products as bestseller_sum', 'bestseller')` — both are `with*` aggregates computed unconditionally on every request (not just when `sort_by=bestseller`), since `bestsellers` is now also part of the response payload, not just a sort key.
- `sort_by` — `newest` (`products_authors.created_at DESC` — also what an omitted `sort_by` resolves to, no separate `default` value/label like Products; same "nothing else meaningful to default to" reasoning as `GET /api/news`), `books` (`products_count DESC`, reusing the same `withCount('products')` aggregate that populates the `books` field), `bestseller` (`bestseller_sum DESC`, reusing the same `withSum` aggregate that populates the `bestsellers` field — same ranking idea as `HomeService`'s `best_author` but ordering the whole list instead of picking a single top author), `oldest` (`products_authors.created_at ASC`).
- **Not cached** — same reasoning as `GET /api/products`: a paginated, sortable listing has too many page/sort_by combinations for a cache to earn its keep, so it's computed fresh per request; only `LayoutService`/`HomeService` (data that's identical for every request) stay cached.

**`GET /api/news`** *(`NewsController` → `NewsFilterRequest` → `App\Services\BlogService::getFilteredList()`/`getCategories()`, powers the News listing page)* — query params `sort_by`, `category`, `page`; response `{items: {data, pagination}, categories, page}`:

- `getBySlug()` matches `status = 1` only — `news_posts` has no archived-but-linkable middle state like `products.status = 2`, just active/inactive, so anything else 404s via `respondWithError('Post not found.', 404)`.

## Caching

`LayoutService::getLayout()`, `HomeService::getHome()`, `ContactService::getContact()`, and `AboutService::getAbout()` are wrapped in `Cache::tags([...])->remember($key, $ttl, fn () => [...])` (Redis, `CACHE_STORE=redis` / `predis` client, both already set in `.env`) — pattern and TTLs modeled on the user's `srelon/demo-news` project's `CacheService`. `App\Services\CacheService` holds the TTL constants (`TTL_LAYOUT = 900s`, `TTL_HOME = 600s`, `TTL_CONTACT = 900s`, `TTL_ABOUT = 900s`) and tag constants (`TAG_LAYOUT`, `TAG_HOME`, `TAG_CONTACT`, `TAG_ABOUT`), plus one `flushOnXWrite()` static method per write source.

**Neither half of `GET /api/products` is cached** — `ProductService::getFilteredList()` (the paginated listing) never was, and `getFilterGroups()` lost its cache once its counts became faceted (depend on the active filter combination, see § API response format). Both have the same "too many distinct combinations for decent hit rate" problem, so both are computed fresh per request. This matches the general rule (see CLAUDE.md § Caching): cache general/shared data by default, skip it for highly-parameterized endpoints and say so rather than force a blanket `remember()` everywhere.

**Cache invalidation is wired via a shared `App\Models\Concerns\FlushesCacheOnWrite` trait**, not manual calls from a controller/service — this project's admin writes go through Filament's own generated CRUD (no custom `AdminService` layer intercepting every save like the reference project has), so a model-level hook is the one place guaranteed to fire regardless of whether the write came from Filament, Tinker, or a future API endpoint. The trait defines `bootFlushesCacheOnWrite()` (Eloquent auto-calls `boot{TraitName}()` for every trait a model uses, so this fires without the model needing its own `booted()` override — and doesn't collide with a model that has its own `booted()` for unrelated logic, e.g. `Order::booted()` generating `public_id`/`txid`) which wires `static::saved()`/`static::deleted()` to `CacheService::{$model::$cacheFlushMethod}()`. Each model just adds `use FlushesCacheOnWrite;` plus a `protected static string $cacheFlushMethod = 'flushOnXWrite';` naming which `CacheService` method to call — 2 lines instead of a duplicated 5-line `booted()` block per model (was manually duplicated across 13 models before 2026-07-04, then extracted). Wired on: `Menu`, `ContactInfo` (→ `TAG_LAYOUT`), `ProductsCategory` (→ `TAG_LAYOUT`/`TAG_HOME`, since a category rename affects the layout's category list and any product card showing that category name), `Product`, `ProductStock`, `ProductImage`, `ProductsAuthor` (all four → `TAG_HOME`/`TAG_LAYOUT` via the same `CacheService::flushOnProductWrite()`, since all of them feed both `HomeService`'s bestsellers and `LayoutService`'s `best_books`), `NewsPost` (→ `TAG_HOME`), `Faq` (→ `TAG_CONTACT`), `TeamMember`/`Perk` (→ `TAG_ABOUT`), `Page`/`SeoMeta` (both → `TAG_HOME`/`TAG_CONTACT`/`TAG_ABOUT` via `CacheService::flushOnPageWrite()` — deliberately broad: `SeoMeta` is polymorphic and also backs `Product`/`NewsPost`/`ProductsCategory` SEO, but only `Home`/`Contact`/`About` are actually cached, so flushing all three tags on every `SeoMeta`/`Page` write is simpler than tracking which specific `type`/`record_id` was touched, at the cost of occasionally flushing a tag that didn't need it).

**Only cache plain arrays, never raw `Collection`/Eloquent model objects** — every cached closure calls `->toArray()` on any `Collection` before returning it (see `LayoutService::getLayout()` / `HomeService::getHome()`, and `formatMenuItem()`'s nested `children` which needs its own `->all()` since `Collection::toArray()` does not recurse into a plain array's own values). This isn't just style: this project's `config/cache.php` has Laravel 13's newer `'serializable_classes' => false` default, which makes Redis's `unserialize()` refuse to reconstruct **any** object read back from the cache — a cached `Collection` silently comes back as `__PHP_Incomplete_Class` on every cache-hit request (first request after a flush works fine since it never round-trips through serialization; every request after that is broken) while cached plain arrays/scalars are unaffected. Fix is to never serialize objects into the cache in the first place, not to loosen `serializable_classes` — that setting is a genuine security control against cache-poisoning object injection, and weakening it project-wide to work around one caching call would be the wrong trade.

## Stock availability

**Implemented 2026-07-04** in `ProductService::formatStock()`/`availableStockQuantity()`, exposed as `stock.quantity` on every endpoint that returns a product card (see `GET /api/products` above). For a given `product_stocks` row, available quantity is:

```
available = product_stocks.quantity
    - SUM(order_items.quantity        WHERE product_stock_id = X AND status = 0)
    - SUM(order_items.fact_quantity   WHERE product_stock_id = X AND status IN (1, 2, 3))
```

**Pending (`status = 0`) reserves by the *ordered* quantity** (`order_items.quantity`) — nothing has shipped yet, so the full ordered amount is provisionally held. **Shipped/delivered/completed (`1`/`2`/`3`) reserve by the *actually fulfilled* quantity** (`order_items.fact_quantity`) instead — once an item has actually left inventory, what matters is how much really went out, not what was originally ordered (an order can be partially fulfilled). Status `4` (cancelled) is excluded entirely — a cancelled order item releases its reservation, whether it was pending or partially fulfilled. The result is floored at `0` (`max(0, ...)`) so a batch that's been over-reserved by test/edge-case data never reports a negative quantity.

Implementation detail: `ProductService::baseQuery()` eager-loads `activeStock` with two `withSum()` aggregates (`pending_quantity` from `orderItems` scoped to `status = 0` summing `quantity`, `fulfilled_quantity` scoped to `status IN (1,2,3)` summing `fact_quantity`) rather than running two extra queries per product in `formatProduct()` — avoids N+1 across a paginated/top-N product list. `withSum()` returns `null` (not `0`) when a stock row has no matching `order_items`, so both are read with `?? 0` before subtracting.
