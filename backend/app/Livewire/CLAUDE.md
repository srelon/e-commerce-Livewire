# CLAUDE.md (admin panel)

Conventions for the Livewire admin panel at `/admin` — everything under `app/Livewire/`, `resources/views/livewire/admin/`, and `resources/views/livewire/components/`. See `backend/CLAUDE.md` for the public API / shop-domain conventions, and root `CLAUDE.md` for Docker/monorepo-wide rules.

Plain Livewire admin — every resource/page (Users, Roles + permission matrix, Admins, Menus tree, Dashboard) uses **Livewire PowerGrid** for tables and **Flux UI (Free tier)** for form components.

## Routing, navigation, namespacing

- **Routing + sidebar nav live in `app/Livewire/Navigation/`**, not `routes/admin.php` (doesn't exist). `routes.php` is a plain procedural route file (no class/namespace) holding every `admin.*` route, loaded from `bootstrap/app.php` via `Route::middleware('web')->group(app_path('Livewire/Navigation/routes.php'))`. `Navigation.php` is a separate PSR-4 class holding the sidebar's `$items` array and `visible(Admin $admin): array`, filtering by `Route::has()` + `$admin->hasAccess()`. The sidebar blade is one generic `@foreach` over `Navigation::visible(...)` — never hand-edit it per nav item. Keep the two files separate: a route file is `require`d directly at boot, a class file is autoloaded on first reference — merging them risks a "class already declared" fatal.
- Every top-level (ungrouped) `$items` entry needs an `icon` key (a bare heroicon slug, no prefix) — `app.blade.php`'s plain `flux:navlist.item` branch renders `:icon="$entry['icon'] ?? null"`, so a missing key silently renders with no icon.
- New admin-panel helper/support classes go under `app/Livewire/` (e.g. `Livewire/Traits/`, `Livewire/Navigation/`) — check there before inventing a new top-level `app/Support/`-style folder.
- **Every actual Livewire component class lives under `App\Livewire\Components\*`** with no extra `Admin\` segment (`Components\Auth\Login`, `Components\Dashboard`, `Components\{Admins,Roles,Users}\{Form,Table,Index}`) — `Livewire` already signals "these are components" the way `Http\Controllers` does for controllers, and `Components` itself separates real components from sibling `Traits`/`Navigation` support code.
- **A resource whose sidebar item belongs to a `Navigation::$items` group gets a matching namespace segment** — `Components\Catalog\{Products,Categories,Authors}`, `Components\Content\News` — mirroring the sidebar groups. Ungrouped resources (`Auth`, `Dashboard`, `Menu`, `Admins`/`Roles`) sit directly under `Components`. This isn't cosmetic: `products_categories` and `news_categories` both want a `Categories` class, and without the group segment they'd collide.
- Blade views under `resources/views/livewire/admin/` mirror the same grouping (`catalog/{products,categories,authors}/*`, `content/news/*`); ungrouped resources keep flat folders. Shared cross-resource partials (`livewire/admin/partials/*`) stay top-level.
- **`resources/views/components/` was moved to `resources/views/livewire/components/`** — every file in it is admin-only, and the bare `components/` name gave no hint of that. `AppServiceProvider::boot()` registers `Blade::anonymousComponentPath(resource_path('views/livewire/components'))` with no prefix, so every `<x-admin.*>`/`<x-lightbox-trigger>` tag is unchanged — only the *string* view-path references changed (`#[Layout('livewire.components.layouts.admin.app')]`). A future anonymous component still goes here, referenced the same `<x-...>` way.

## Delete confirmations, RBAC, layout-refresh pattern

- **Delete confirmations go through `App\Livewire\Traits\ConfirmsAction`**, never native `confirm()`/`wire:confirm`. A component `use`s the trait, includes `@include('livewire.admin.partials.confirm-modal')` once, and triggers via `$wire.dispatch('confirm-action', { event, params, message, heading, label, variant })`. The target method needs `#[On('...')]` matching the event name, with params matching keys by name (Livewire binds by name, not position).
- **Two `ConfirmsAction`-using components mounted on the same page at once must use `$wire.dispatchSelf('confirm-action', {...})`, not plain `dispatch()`.** `dispatch()` is page-wide, so every mounted listener receives it — hit this with the News category/author managers (both embedded on one page) and again with product gallery delete vs. `ReviewsPanel`'s own delete (always mounted together on the product edit page). `confirm-modal.blade.php` takes an optional `name` prop for exactly this (each simultaneously-mounted component needs its own uniquely-named `flux:modal`, since `dispatchSelf` alone doesn't give two same-named Flux modals distinct identity). **Any future page mounting more than one `ConfirmsAction` component must use `dispatchSelf`.**
- **RBAC**: `App\Models\Admin::hasAccess()` (the `admin_role_access` pivot) drives access via `App\Livewire\Traits\HasAccessControl` — `hasAccess(string $type)`, `guardView()` (call in `mount()`, aborts 403), `guardSave()` (call at the top of every mutating action, toasts + returns `false` on denial). `hasAccess()` must be **public** — Blade views call `$this->hasAccess(...)` directly and can't reach a protected method.
- **Gotcha: plain Blade markup living in `components/layouts/admin/app.blade.php` (outside any Livewire component's own render boundary) never reflects a change from an in-place `save()`** — only from a `wire:navigate` redirect or hard reload. Livewire's morph only touches the saving component's own `wire:id` root; the layout is server-rendered once at page load. Fix: extract the fragment into its own tiny Livewire component (fresh data in `render()`) with an empty-bodied `#[On('some-event')]` listener the mutating action dispatches. Two real instances: `Components\HeaderProfile` (listens `profile-updated`, from `Admins\Form`/`Admins\Profile::save()`) and `Components\SidebarNav` (listens `admin-access-updated`, from `Roles\Form::persist()`, `Admins\Form::persist()`, `Roles\Table::deleteRole()` — any future write touching `admin_role_access` or an admin's `role_id` needs the same dispatch). Both sit directly under `Components\` (chrome, not a resource's own CRUD) but their Blade views deliberately break the namespace-mirrors-view-folder convention, living in `resources/views/livewire/components/layouts/admin/` next to `app.blade.php`/`guest.blade.php` — a one-off exception, don't generalize it.

## Schema-driven forms

- **Forms are schema-driven, not hand-written per resource.** A form component exposes `#[Computed] schema(): array` (`name`/`label`/`type`/`options`/`disabled`/`placeholder`/`preview`/`full_width`; `type` selects the `fields/*.blade.php` partial: `text` with `input_type`, plus `select`/`file`/`textarea`/`richtext`/`gallery`). `render()` returns the shared `livewire.admin.partials.resource-form` view, passing `page_title`/`fields`/`disabled`/`cancel_route` and, when needed, `extra`/`extra_data` for non-schema markup (e.g. Roles' permission matrix).
- **The view-data key is `page_title`, not `title`** — a schema field literally named `title` (Products, News) binds to a same-named public property, which silently shadows a passed `title` array key via Livewire's view-data merge.
- `components/admin/form-fields.blade.php` renders every field (including `file` and any `full_width`) inside one shared bordered grid box — field partials must not carry their own border/bg/padding.
- **`save()`/`saveAndExit()` are shared via `App\Livewire\Traits\HandlesFullPageSave`**, generic off three properties: `$routePrefix`, `$routeParamKey` (usually matches `$routePrefix` singularized — News's is `'post'`, not `'news'`), `$saveMessageName`. Each component still owns its own `persist(): ?Model`.
- **`render()` never builds a hand-written `view('...', [...])` array literal** — use the named-parameter helpers instead:
  - `HandlesFullPageSave::renderResourceForm(pageTitle, disabled, cancelRoute, siteUrl = null, deleteAction = null, deleteMessage = null, extra = null, extraData = [], view = 'livewire.admin.partials.resource-form', viewData = [])` — pulls `fields` from `schema()` internally. `view`/`viewData` are the escape hatch for a resource with its own wrapper view (e.g. `Products\Form`).
  - `RendersResourceTable::renderResourceTable(pageTitle, tableComponent, createRoute = null, createLabel = null, extra = null, extraData = [])` — used by every `Index` alongside `ConfirmsAction`/`HasAccessControl`.
- **`x-admin.resource-header`'s `deleteAction`/`deleteMessage` props** put a Delete button next to "View on site" via the same `ConfirmsAction` flow. **Never build its confirm payload with `@js()` inline inside a `<flux:button>` attribute** — Flux's custom tag compiler pre-parses its own attributes before Blade directive compilation reaches them, so `@js()` there silently fails to compile (the literal string shows up in rendered HTML), and wrapping in `e(json_encode(...))` double-escapes. Use a `data-delete-confirm="{{ json_encode(...) }}"` attribute (plain `{{ }}`, no `e()`) read back via `JSON.parse($el.dataset.deleteConfirm)` in `x-on:click`.
- **A `select` field's `<flux:label>` can carry a trailing icon-button via `'manage_button' => ['label' => ..., 'dispatch' => 'event-name']`** (Flux's built-in `<x-slot:trailing>`, not a hand-rolled wrapper div). The button needs `x-on:click.stop` — Flux's own label-click handler focuses the nearest input on any click except one landing on an `a`/`button`, and a bare SVG icon child isn't itself a `button`.
- **A `select` field can opt into `wire:model.live` via `'live' => true`** — used by Menu's Type/Route fields, which need an immediate round-trip to swap dependent fields server-side. Implemented as two full `@if`/`@else` `<flux:select>` blocks, not a conditional `.live` suffix on the attribute name — a dynamic Blade construct inside a `<flux:...>` tag's *attribute name* throws a parse error (same root cause as the `@js()` gotcha above: Flux's tag compiler can't handle Blade landing inside the attribute itself).

## Modal forms, embedded managers, shared traits

- **A modal-based create/edit form uses `x-admin.modal-form`** (`components/admin/modal-form.blade.php`) — same `x-admin.form-fields` fields, wrapped in `flux:modal`. Props: `name`, `title`, `fields`, `disabled`, `model` (default `show_modal`), `saveAction`/`cancelAction` (default `save`/`closeModal`), `class` (width). The component still owns its own `schema()`/`save()`. The default slot renders **inside** the fields' bordered grid box as an `sm:col-span-2` cell (guarded by `$slot->isNotEmpty()`), not as a separate block below it — used e.g. by Menu\Form's Target slug-search field.
- **"Embedded manager" components** — a browse-table-plus-create/edit-form pair living entirely inside modals launched from a *different* page (`Components\Content\News\{CategoryManager,AuthorManager}`, triggered by `manage_button` on News\Form's select fields). A third shape alongside full-page `Index`+`Form` and modal-`Form`: two stacked modals (`show_list_modal` plain-HTML-table browse + `show_form_modal` inner `x-admin.modal-form`). Native `<dialog>`-backed Flux modals stack correctly with no extra wiring. Saving/deleting dispatches a plain page-wide event (`news-categories-updated`/`news-authors-updated`) that News\Form catches via an empty `#[On(...)]` handler to force a re-render of its own `#[Computed]` `categories()`/`authors()`.
- **The two managers' PHP was ~90% identical (both ~140 lines) — consolidated into `App\Livewire\Traits\HandlesEmbeddedManager`** (2026-08-17, direct user request: "почти полный копипаст, можно создать один общий компонент"), composing `ConfirmsAction`+`HandlesModalForm` and owning `list()`/`schema()`/`openList()`/`openEdit()`/`resetForm()`/`modalProperty()`/`save()`/`performDelete()` **and its two `#[On(...)]` listeners** in full — nothing Livewire-lifecycle-related is left in the concrete classes at all. Each concrete manager is down to ~65-70 lines: **config as plain properties** (`$modelClass`, `$countRelation`, `$updatedEvent`, `$itemNoun`, `$formFieldNames`, `$listColumns`, `$managerEventKey` — matching `HandlesFullPageSave`'s existing `$routePrefix`/`$routeParamKey` pattern, not abstract getter methods) **plus 3 optional no-op hooks** (`extraListFields($model)`, `extraSchemaFieldsBefore()`, `beforeSave($model, $isCreating)`) for the genuinely different bits (Category generates a slug on create; Author uploads/previews an avatar). Deliberately **not** the `HandlesSortableOrder`-style 4-6-hook design already rejected once in this codebase for fragmenting a single readable method across files (see [[feedback-dedup-abstraction-limit]]) — the difference here is scale: that case saved ~10 lines across 3 call sites, this one saves ~75 lines per consumer, so the same fragmentation tradeoff lands the other way.
  - **`openList()`/`performDelete()` moved fully into the trait using Livewire's dynamic event-name placeholders** (`#[On('open-{managerEventKey}-manager')]` / `#[On('delete-{managerEventKey}')]`) — a first pass (same day) assumed this was impossible ("PHP attributes need compile-time-literal arguments, so the event name can't come from a trait property"), which is true of the *attribute value itself*, but Livewire resolves `{propertyName}` placeholders inside that literal string at listener-registration time via `data_get($component, $propertyName)` (`SupportEvents::replaceDynamicPlaceholders`, applied uniformly to both `#[On(...)]`-attribute-derived and `getListeners()`-derived listeners) — this is an official, documented Livewire 3 mechanism (their own docs use it for per-model scoping, e.g. `#[On('post-updated.{post.id}')]`), not an internal implementation detail being relied on unsafely. Each concrete manager just declares `public string $managerEventKey = 'news-category'` (or `'news-author'`) and the trait derives everything else from it — including `modalListName()`/`modalFormName()`/`confirmModalName()` (public methods returning `"{$managerEventKey}-list"` etc., replacing what used to be explicit `name`/`formName`/`confirmName` blade props) and `deleteMessage(string $name)` (`"Delete ".Str::lower($this->itemNoun)." \"{$name}\"?"`, replacing a `deleteMessageTemplate` prop). **The general lesson: before concluding "X must stay per-subclass because of a PHP/Livewire attribute constraint," check whether the specific piece that varies (here, just the event *name* string) can be factored out through a placeholder rather than assuming the whole method has to move.**
- **Blade side: `x-admin.manager-list-modal` (chrome) + `x-admin.manager-table` (the table itself), both in `resources/views/livewire/components/admin/`.** `manager-list-modal` now takes only `heading`/`createLabel`/`formTitle` as props — `name`/`formName`/`confirmName` used to be explicit props too, until they turned out to be 100% mechanically derivable from `$managerEventKey` (see above), so it now calls `$this->modalListName()`/`$this->modalFormName()`/`$this->confirmModalName()` directly. It renders the outer `flux:modal`+heading+Close button+`x-admin.modal-form`+`confirm-modal` include, with its default slot holding whatever `manager-table` instance the caller composes inside it. A first pass reasoned that Blade anonymous components have no Vue-style scoped-slot mechanism to hand `$item` into a slot on each `@foreach` iteration, so the `<table>` itself was left unextracted — sidestepped, not actually blocking: **`manager-table` takes `columns` (array of `{key, label, type}`) + `items` + `emptyMessage`, and dispatches each `<td>` to `@include("livewire.admin.partials.list-columns.{$column['type']}", ['row' => $row, 'column' => $column])`** — the exact same type-driven-partial mechanism `fields/*.blade.php` already uses for schema-driven form fields (see "Forms are schema-driven" above), just applied to table columns instead of form fields. Column types so far: `text` (plain value), `badge` (Active/Inactive), `avatar` (image-or-fallback-icon). `CategoryManager`/`AuthorManager` each declare a **public** `$listColumns` property (must be public, not protected like the trait's other config properties — Livewire's public-property-to-view-data injection only covers public properties, and this one is read directly in the component's own top-level Blade view via `:columns="$listColumns"`). Delete confirmation's message uses `\Illuminate\Support\Js::from($this->deleteMessage($row['name']))` rather than the original hand-rolled `&quot;`-escaped string concatenation — genuinely safer (handles an apostrophe in a name correctly, e.g. "O'Brien"), not just equivalent. The delete dispatch's `params` key is always a plain `id` now (was `categoryId`/`authorId`) since nothing downstream needs the old per-resource name anymore. **End result: each manager's own Blade view (`category-manager.blade.php`/`author-manager.blade.php`) is 11 lines — just the page-specific copy (heading, create-label, form title, empty message) and its `$listColumns` config, nothing structural.** A third "embedded manager" needing a new column shape only needs a new `list-columns/{type}.blade.php` partial, not changes to `manager-table` itself.
- **Gotcha found via this work: a soft-deleting model's slug-uniqueness check must use `withTrashed()`, or a re-created record with the same name can never save again.** `NewsCategory` uses `SoftDeletes` — `CategoryManager::uniqueSlug()`'s `NewsCategory::where('slug', $slug)->exists()` (pre-existing, not introduced by the refactor above) excludes soft-deleted rows by Eloquent's default scope, so creating, deleting, then re-creating a category with the same name generated the *same* slug both times — the second `INSERT` then failed with a raw `UniqueConstraintViolationException` 500 (MySQL's unique index doesn't know or care about `deleted_at`), not a clean validation error. Fixed with `NewsCategory::withTrashed()->where('slug', $slug)->exists()`. Any other `uniqueSlug()`-style generator against a `SoftDeletes` model needs the same `withTrashed()`.
- **Gotcha found while building the above: a Blade anonymous component does *not* inherit the calling view's ambient variables, only `$this` and its declared `@props`/attributes.** `confirm-modal.blade.php` read `$confirm_action_heading` etc. as bare variables — worked fine via a plain `@include` from a component's own top-level view (where Livewire's public-property-to-view-data injection puts them directly in scope), but broke (`Undefined variable`) once the same `@include` moved *inside* `x-admin.manager-list-modal`, since anonymous components get their own isolated variable scope. Fixed by reading `$this->confirm_action_heading` etc. instead — `$this` correctly resolves to the Livewire component instance at any include depth (already proven by `modal-form.blade.php`'s own `$this->hasAccess()` calls), so this is strictly safer than the bare-variable form and works identically for every existing caller of `confirm-modal.blade.php` (PowerGrid tables, `Categories\Form`, etc. — regression-tested, unaffected). **Any future shared Blade partial reading a caller's plain variable (not a prop) is one nested-anonymous-component away from silently breaking** — prefer `$this->property` over a bare variable in a partial meant to be `@include`d from more than one nesting depth.
- **`closeModal()`/`resetForm()` are shared via `App\Livewire\Traits\HandlesModalForm`** — `resetFormFields(array $properties)` calls Livewire's own `$this->reset($properties)` so defaults live only on the property declaration, never duplicated. Also folds in `resetErrorBag()` + `dispatch('admin-form-reset')`. `closeModal()`'s target property defaults to `show_modal`; the two News managers override via a **method** `modalProperty(): string`, not a re-declared property — PHP fatals ("definition differs and is considered incompatible") if a class redeclares a trait's property with a different default, but method overrides always work.
- **`resetFormFields()` itself actually lives on `App\Livewire\Traits\HasFormHelpers`, which `HandlesModalForm` composes** (see `HasFormHelpers` in the dedup-sweep section below) — added 2026-08-16 after `Catalog\Products\ReviewsPanel` (an inline reply/edit form embedded in the product page, not a modal popup) was found still hand-resetting `cancelReply()`/`cancelEdit()` property-by-property instead of using this helper. **A component with a "cancel"/"clear" method that hand-assigns 2+ properties back to their literal declared defaults should reach for `resetFormFields()`, whether or not it has a modal** — this was found by an explicit sweep for the pattern after the first miss, not caught by the original `HandlesModalForm` work. The sweep also caught `Admins\Profile::updatedModeratorSearch()` doing the same manual 3-property reset — fixed with plain Livewire-native `$this->reset([...])` instead, **not** `resetFormFields()`, since this method runs on every keystroke of a live search (`wire:model.live` on the search input) and `resetFormFields()`'s `dispatch('admin-form-reset')` is meant for an actual form-cancel action, not a per-keystroke event — dispatching it that often would be semantically wrong even though harmless in practice. `resetFormFields()` vs. plain `reset()` is a real choice, not just "always use the helper": reach for the `resetFormFields()` version only when clearing an actual buildable form (needs the error-bag reset + file-field-blob-reset side effects too), plain `reset()` for anything else.
- **Every popup submits its primary action on Enter**, via one of three mechanisms depending on content — never a nested `<form>`:
  - `x-admin.modal-form` and any hand-rolled popup embedded inside another form's own `<form wire:submit="...">` (e.g. `permission-matrix.blade.php`'s "Add Access" modal) wrap content in `<div x-on:keydown.enter="if ($event.target.tagName !== 'TEXTAREA') { $event.preventDefault(); $wire.{action}() }">`. A real nested `<form>` was tried first and silently vanished from the DOM — HTML5 forbids nested forms, the inner tag is dropped with no warning, breaking Enter-to-submit and risking Enter submitting the *outer* form instead. This is why the `x-on:keydown.enter` approach is used even for standalone-page popups where a real form would've been fine — one consistent mechanism.
  - `confirm-modal.blade.php` needs no JS at all — a plain `autofocus` on the confirm button; `<dialog>`'s `showModal()` auto-focuses it, and Enter activates the focused button natively.

## The August 2026 dedup sweep

Four narrowly-scoped traits, extracted after a full sweep deduplicated copy-pasted boilerplate — don't reintroduce the duplicates they replace:

- **`HasPublishableContentFields`** bundles `title`/`slug`/`category_id`/`author_id`/`published_at`/`seo_title`/`seo_description`/`seo_keywords` plus their fill/validate/persist helpers (`fillTitleSlug()`, `slugValidationRule(string $table, ?int $ignoreId)`, `fillPublishedAt(?Carbon $date)`, `publishedAtValidationRule()`, `parsePublishedAt(): ?Carbon`, `fillSeoFields(?SeoMeta $seo)`, `seoValidationRules()`, `saveSeoFields(Model $model)`) — the full field set of "a publishable catalog/content entry," used by `News\Form`/`Products\Form` (the only two resources with these fields, and always all of them together — a first pass on 2026-08-16 split this into 4 separate traits reasoning a future resource might want only one piece, but merged back into one file the same day since that hadn't happened and 4 files each holding one tiny slice was worse in practice than one cohesive trait both real consumers need in full). `mount()` calls `fillTitleSlug()`/`fillPublishedAt()`/`fillSeoFields()`; `persist()` spreads `...$this->slugValidationRule(...)`/`...$this->publishedAtValidationRule()`/`...$this->seoValidationRules()` into `validate()` and calls `saveSeoFields($model)`/`parsePublishedAt()`. If a third resource grows this same field set, reach for this trait rather than re-declaring the properties — if it only wants *some* of the fields, that's the point at which splitting it back apart would be justified, not before.
- **`HasFormHelpers`** bundles two small, unrelated-in-purpose but both genuinely multi-consumer helpers: `previewUrl(array|string|null $image): ?string` (builds a `Storage::disk('public')->url(...)` preview — accepts either the JSON `{original: ...}` shape used by Products/Categories/Authors/News images, or a plain string path like an avatar column, branching on `is_array()`) and `resetFormFields(array $properties): void` (calls Livewire's own `$this->reset($properties)` + `resetErrorBag()` + `dispatch('admin-form-reset')`, so a "cancel"/"clear" action never hand-assigns each property back to its literal default). Composed by `HandlesModalForm` (so `Categories\Form`/`Authors\Form`/`Menu\Form`/the two News managers get both methods for free without a separate `use` line) and by `HasAccountFields` (so `Users\Form`/`Admins\Form`/`Admins\Profile` get `previewUrl()` for their avatar without their own copy) — `News\Form`/`Products\Form`/`ReviewsPanel` (which have neither `HandlesModalForm` nor `HasAccountFields`) `use` it directly. **This one *is* a deliberate grab-bag**, unlike the "four small, narrowly-scoped traits, not one" philosophy the original August sweep established — two single-method traits (`HasImagePreview`, `ResetsFormFields`) existed briefly before this, and were merged into one file specifically because neither was substantial enough on its own to justify being a separate file everyone had to know about; if either one grows real additional behavior of its own later, split it back out then, not preemptively. Gained `statusField(): array` in the same 2026-08-16 pass below.
- **A `schema()` field entry can be a shared method call instead of a literal array — but only for a field genuinely byte-identical across 3+ consumers, not for "looks similar."** `backend/app/Livewire/CLAUDE.md`'s own "Forms are schema-driven" section intentionally keeps schema arrays literal/inline for discoverability (one glance at a component tells you every field it has) — extracting a field into a helper trades that off for DRY, so it's only worth it where the array really is copy-pasted unchanged. Audited all 11 `schema()` methods (2026-08-16, prompted directly by the user asking to check) and found exactly two things worth extracting, both already living in a trait the affected components already `use`:
  - **`HasFormHelpers::statusField(): array`** — the `{name: status, label: Status, type: select, options: [{1: Active}, {0: Inactive}]}` block was byte-identical across `Categories\Form`, `News\CategoryManager`, `News\AuthorManager`, `News\Form` (all reachable through `HasFormHelpers`, directly or via `HandlesModalForm`'s composition — none needed a new `use` line). **Not** used by `Products\Form`, whose `status` is a 4-value enum (Created/Active/Archived/Reserved) — a genuinely different field, not the same one almost-matching.
  - **`HasAccountFields::accountAvatarField(?string $avatarPath): array` / `accountPasswordField(bool $isEditing): array`** — `Users\Form`/`Admins\Form`/`Admins\Profile` (the same trio `HasAccountFields` already covers) had an identical avatar-file field (`h-16 w-16 rounded-full`) and an identical password field (`Leave blank to keep current password` placeholder, gated on whether a record already exists) — both call sites take the model-specific value (`$this->user?->avatar`, `(bool) $this->admin`, `true` for `Profile` since there's no create mode) as a param rather than reading `$this->{property}` internally, so the helper stays reusable rather than assuming which property name the caller happens to use. The `name` field between them (`{name: name, label: Name, type: text}`, appears in 9 of the 11 `schema()` methods) was deliberately **not** extracted — one line, and forcing it through a helper call would cost more in "go look at the trait to see what this renders" than it saves.
  - **Found in passing while auditing, fixed regardless of the dedup question:** `News\AuthorManager` built its avatar preview with a raw `$author?->avatar ? Storage::disk('public')->url($author->avatar) : null` ternary in both `list()` and `schema()`, despite already having `previewUrl()` available for free through `HandlesModalForm` → `HasFormHelpers` — a leftover from before that composition existed. Swapped both to `$this->previewUrl($author?->avatar)`.
- **`HandlesRichText`** (renamed from `HandlesRichTextImages`) — `handleRichTextImageUpload()` plus `sanitizeContent(string $html): string`. Reach for this on any future richtext field, not a re-derived allowlist.
- **`HasPowerGridBehavior::setUp(): array`** — the `PowerGrid::header()->showSearchInput()` / `footer()->showPerPage()->showRecordCount()` pair, now the default for all 6 `Table.php` components. Plus closure helpers: `avatarCellField()`, `imageCellField(Closure $imageResolver)`, `booleanIconField(Closure $valueResolver)`.
- **`HandlesModalForm`** gained `openCreate(): void` (guard `hasAccess('edit')`, `resetForm()`, open via `modalProperty()`) and `closeListModal(): void`. **`openEdit()` was deliberately left un-abstracted** — the middle (which model fields map to which properties) is genuine per-resource logic, not boilerplate worth a template-method hook pair.

**Gotcha: a trait's default `mount()` silently overrides a parent class's real `mount()`, since PHP's MRO is own class → traits → parent class.** Adding a default `mount()` to `HasAccessControl` (used by both `Index`/`Form` pages *and* every `Table.php extends PowerGridComponent`) broke every table with `500 — View [] not found`, since PowerGrid's own `mount()` does real internal setup the trait's version skipped — nothing in the stack trace pointed at the trait. **Before adding a default method to a trait, check every class that `use`s it for a base class of its own.** Fixed by moving the default `mount()` into `RendersResourceTable`/`HandlesModalForm` instead — neither is used by anything extending `PowerGridComponent`.

**`saveOrder(array $tree)` stays a plain, self-contained method per component (`Menu\Form`, `Categories\Form`, `Products\Form`'s gallery) — a shared `HandlesSortableOrder` trait (4 hook methods) was tried and reverted the same day.** It removed the duplication but scattered one previously-readable method across a wrapper + 3-4 hooks, worse for readability than ~10 duplicated lines across 3 call sites. **Don't re-attempt this abstraction.**

**`FlushesCacheOnWrite::bulkUpdateAndFlush(iterable $rows, callable $attributesFor)`** — closes the gap where a bulk `Model::whereKey($id)->update([...])` never fires the `saved` event `bootFlushesCacheOnWrite()` relies on:

```php
public static function bulkUpdateAndFlush(iterable $rows, callable $attributesFor): void {
    foreach ($rows as $index => $row) {
        static::whereKey((int) $row['id'])->update($attributesFor($row, $index));
    }
    CacheService::flush(static::$cacheFlushTrigger);
}
```

`Categories\Form::applyOrder()` → `ProductsCategory::bulkUpdateAndFlush(...)`; `Products\Form::applyOrder()` → same on `ProductImage`. Any future bulk-write against a `FlushesCacheOnWrite` model should use this instead of a raw `whereKey()->update()` + manually-remembered flush. `Menu` doesn't need it — `persistOrder()` calls `update()` on hydrated instances, which already fires the event.

## Field types and components

- **`type: 'richtext'` is backed by Tiptap Core** (vanilla `@tiptap/core` + starter-kit + image + placeholder), not a hand-rolled contenteditable — `document.execCommand` was tried first and rejected same-day for unreliable toggle/exit semantics (headings wouldn't un-toggle, no way to exit a blockquote). `resources/js/rich-text-editor.js` (`Alpine.data('richTextEditor', ...)`) mounts the editor with headings restricted to H2/H3 (matching `sanitizeContent()`'s allowlist).
  - **Gotcha: never store the Tiptap `Editor` instance as `this.editor` inside an Alpine `x-data` factory's returned object.** Alpine wraps the returned object in a reactive `Proxy`, and ProseMirror's transaction dispatch does strict object-identity checks — a Proxy-wrapped editor throws `RangeError: Applying a mismatched transaction` on nearly every interaction. Fix: keep it in a plain closure variable (`let editor = null` outside the returned object), never `this.editor`. General lesson for any complex stateful JS class instance held by an Alpine component, not Tiptap-specific.
  - **Gotcha: the editor's root `<div x-data="richTextEditor(...)">` needs `wire:ignore`** (not `.self`) — its `x-data` seed (`@js($this->content)`) drifts from the live value the moment the user edits anything (the hidden `wire:model` textarea marks itself dirty), so any subsequent Livewire round-trip (including the two-step file-upload request pair) makes the seed string differ, and Livewire's morph tears down the live Alpine scope — orphaning the image-insert listener and the live editor mid-flow.
  - **Value plumbing**: schema entry needs explicit `'value' => $this->{field}` — `wire:model` can't bind Tiptap's self-managed DOM, so the partial seeds `content` via `@js($field['value'])` at construction and a hidden `<textarea wire:model="{field}">` is kept in sync by `onUpdate` rewriting its `.value` + firing a native `input` event.
  - **Image upload**: toolbar button → hidden `<input type="file" wire:model="{field}_image">`; the component needs `public ${field}_image = null` + `updated{Field}Image()` calling `HandlesRichText::handleRichTextImageUpload($file, '{field}', $storageFolder)`, which dispatches `richtext-image-inserted` (field-scoped, since it's a page-wide browser event).
  - **Output is still sanitized server-side** via `News\Form::sanitizeContent()` (through `HandlesRichText`) — Tiptap only constrains the editor UI, not a paste from elsewhere. Allowlists `p br h2 h3 ul ol li blockquote strong b em i u a img` via `strip_tags()`, then a second regex pass rebuilds `<a>`/`<img>` keeping only `href`/`src`/`alt` (blocking `javascript:`, forcing `target="_blank" rel="noopener noreferrer"`) — `strip_tags()` alone doesn't strip dangerous *attributes* on allowed tags.
- **`type: 'gallery'` (`Products\Form`'s `product_images`) manages a full multi-image gallery** — upload, delete, drag-reorder — replacing the earlier single "Cover image" field. `Product::primaryImage` (lowest `sort_order`) is unaffected — dragging any image to the front makes it the cover for free.
  - Reorder reuses `sortableTree()` as-is (a flat gallery is a tree whose nodes never have `children`) — same markup pattern, different visual (image thumbnail grid vs. list rows), and the same "Save order"/"Cancel" manual-save pattern (not auto-save-on-drop).
  - New uploads apply immediately in edit mode; in create mode (`product_images.product_id` not nullable, no row to attach to yet) they queue as pending uploads and drain via `storeGalleryFiles()` right after `$product->save()` in `persist()`.
  - Delete/reorder push a fresh list via a `gallery-updated` event (`{field, images}`) — same "Livewire `x-data` seed is one-time-only" resync pattern as the Menu tree.
- **`x-admin.line-chart`** (Chart.js, loaded globally via `window.Chart`) — a pure presentational anonymous component (`title`, `label`, `labels`/`values`, optional `color`), lazy-instantiates on first show and `.resize()`s rather than re-instantiating on toggle. Data prep stays on the calling component (e.g. `Users\Index::mount()`'s daily-registrations query) — reuse this for any future "X per day" chart rather than duplicating the Chart.js/Alpine boilerplate.

## Naming conventions

- **A component owning both a listing/tree and a create/edit modal is named `Form`, never `Index`/`Tree`** (`Categories\Form`, `Authors\Form`, `Menu\Form`) — `Index` undersells the modal/schema/save logic it also owns. A resource either has a separate `Index`+`Form` pair (full-page) or a single `Form` doing both (modal) — never both patterns on one resource.
- **Authors moved from full edit page to `x-admin.modal-form`** — the old `Index`+`Form` pair collapsed into one `Authors\Form`; `admin.authors.create`/`.edit` routes are gone. Since `Authors\Table` is a separate component from `Authors\Form`, its Edit button uses `HasPowerGridBehavior::editModalButton(string $event, array $params)` (dispatches a browser event instead of linking a route) caught via `#[On('open-author-form')]`. The reverse direction (table refetch after save) uses PowerGrid's own `pg:eventRefresh-{tableName}` listener. Any future PowerGrid-table resource moving to modal editing needs this same three-part shape.
- Categories' computed list is named `tree()` (not `list()`), matching Menu\Form — both feed `sortableTree()`. News's `CategoryManager`/`AuthorManager` deliberately keep `list()` — they're a plain server-side `@foreach` table with no drag-sort, so "list" is accurate there. Products\Form's gallery keeps its own `galleryImages()`/`images:` naming (single schema field's data, not a whole-page computed).

## Toast notifications

Two mechanisms depending on whether the action redirects. Same-page actions use `$this->dispatch('notify', type: ..., message: ...)`, caught by `x-on:notify.window` in the layout. Actions that redirect (`redirectRoute(..., navigate: true)`) must `session()->flash('notify', [...])` instead and let the layout's `x-init` fire it from session state — a `dispatch()` right before a `wire:navigate` redirect fires on the page that's about to be torn down and is lost. Don't "fix" a missing toast-after-redirect by moving the dispatch earlier; switch to the session-flash path.

## Alpine + Livewire + drag-and-drop gotchas

These apply to the Menu tree editor and any future Alpine-heavy drag/sort component:

- **Gotcha: never give an Alpine `x-data` object a method with the same name as a Livewire action in the same scope.** `MenuTree`'s Alpine object had its own `save()` — every `wire:click="save"` in that subtree (including an unrelated modal's Save button) silently called the Alpine method instead of the PHP action, no error, since Alpine's scope resolution finds the closest `x-data` key before falling through to Livewire's action binding. Fixed by renaming Alpine methods (`save` → `commitOrder`, `cancel` → `cancelOrder`). Check any future Alpine-heavy component's method names against every `wire:click` in that subtree.
- **Menu tree requires a manual "Save changes" click, not auto-save-on-drop** — tried repeatedly and abandoned after auto-save kept racing the drag library's own DOM mutations (duplicate saves, saves mid-drag). Don't re-attempt without the user explicitly asking again.
- **Gotcha: forcing Alpine re-init via a changing `wire:key` races `@alpinejs/sort`.** Bumping a `public int $version` + `wire:key="menu-tree-{{ $version }}"` made Livewire wholesale-replace the subtree, and the sort plugin's synchronous `x-sort:item` evaluation fired before `x-for` finished establishing loop-variable scope for freshly-inserted clones (`ReferenceError: node is not defined`, first render only). Fixed by dropping the trick: after a structural mutation, `unset($this->tree); $this->dispatch('menu-tree-updated', tree: $this->tree);`, and the persistent (never-remounted) `x-data` root listens via `x-on:menu-tree-updated.window` and reassigns its local array directly — pure Alpine reactivity, no morph involved.
- **Gotcha: even without `wire:key`, a changing `x-data` attribute *value* still makes Livewire silently recreate Alpine's scoped data object on morph, orphaning existing effects.** `unset($this->tree)` before each re-render (the fix above) means the `x-data="menuTree(@js($this->tree))"` seed value genuinely differs on every response even though the element itself never gets replaced. Symptom: works after the first save, but a second local mutation updates the new data object while `x-show="is_dirty"`'s effect stays bound to the orphaned old one — "Save changes" never reappears, and Alpine's next mutation-observer pass throws the same `ReferenceError: node is not defined` as the sort-plugin gotcha above (different trigger, easy to misattribute). Fixed with `wire:ignore.self` on the `x-data` root — Livewire stops touching that element's own attributes on morph while still morphing non-ignored children (the create/edit modal) normally. `wire:ignore` on child elements alone didn't help — the root's own attribute churn was the cause.
- **Gotcha: SortableJS's drag-preview DOM manipulation races Alpine's built-in `MutationObserver`**, throwing `ReferenceError: node/child is not defined` mid-drag. In `forceFallback` mode SortableJS relocates real `<li>` elements (with their baked-in `x-sort:item`/`x-text="node.name"` attributes) outside the `x-for` loop scope Alpine's bookkeeping expects; Alpine's global observer auto-initializes directives on any newly-appeared node, including ones a 3rd-party library moved — not silenced by `wire:ignore`. Fixed via `Alpine.stopObservingMutations()`/`Alpine.startObservingMutations()`: both sortable `<ul>`s' `x-sort:config` wire `onChoose`/`onUnchoose` (hooks the plugin itself doesn't use) to pause before drag-induced DOM movement and resume via `setTimeout(..., 0)` (a macrotask, guaranteed after Alpine's microtask-queued `x-for` repaint).

## Tailwind/Flux/PowerGrid theming

- **Gotcha: PowerGrid's `dist/tailwind.css` is a static snapshot, not a theme source — importing it directly leaves `--color-pg-primary-*`/`--color-pg-secondary-*` undefined in this app's build**, since it only contains whatever classes PowerGrid's own demo happened to use (broke the pagination nav completely, looked fine for `pg-btn-white` since that one happened to be baked in). Fixed in `resources/css/app.css` by **not** importing that file — define `--color-pg-primary-*`/`--color-pg-secondary-*` directly in the app's own `@theme` block (mapped to `zinc`/`amber`), add `@source` entries for PowerGrid's Blade/theme/JS files so its class-name strings get scanned, and re-declare the custom `@apply` classes (`pg-btn-white`, `pg-filter-container`, `pg-enabled-filters-base`) in `@layer components`. Any future "just import our compiled CSS" package needs the same check.
- **Flux UI's default accent is literally black-and-white** (`--color-accent: var(--color-zinc-800)`) — a neutral placeholder, not a real default. Set here to `amber-600`/`amber-500` (dark) in the app's `@theme` block.
- **Gotcha: never hardcode `->orderBy()`/`->orderByDesc()` inside a PowerGrid `datasource()` — it silently breaks every column's `->sortable()`.** `PowerGridComponent` already applies `->orderBy($sortField, $sortDirection)` (its own `Concerns/Sorting` properties) on top of `datasource()`'s query; a hardcoded `orderBy('id', 'desc')` in `datasource()` stacks additively with PowerGrid's own click-triggered `orderBy()` — since `id` is unique, it fully determines row order and every other column's click-to-sort becomes silently inert. Fix: set the default sort via overriding `public string $sortField`/`$sortDirection` as component properties instead — done this way in `Users\Table`, `Roles\Table`, `Admins\Table`.
- **Corollary: a `->sortable()` column bound to a computed `fields()` value must sort by the real underlying DB column** via `Column::make($title, $field, $dataField)`'s third argument (e.g. `Column::make('Verified', 'email_verified', 'email_verified_at')`) — a `fields()`-only closure value can be displayed in PHP but has no SQL to sort/search/filter against.
- **Gotcha: any way of ending up on a page number beyond the real last page — deleting the last row(s) on the last page, manually editing `?page=` in the URL, or changing per-page while sitting on a now-too-high page — shows "No records found" with the pagination footer gone and no way back.** PowerGrid's page number lives in Livewire's own `$this->paginators['page']` (via the stock `WithPagination` trait `PowerGridComponent` already `use`s) and is never revalidated; Laravel's `Builder::paginate()` happily returns an empty `items()` for a page beyond `lastPage()`, it doesn't clamp on its own. First fix attempt (2026-08-16) only patched the delete path — user immediately pointed out the same break happens from a raw `?page=6` URL edit or a per-page change, neither of which goes through a delete handler at all, so the real fix needs to run on every request that could leave the page number stale, not just delete.
  - **`HasPowerGridBehavior::clampPageToValidRange()`** — computes `lastPage` from `$this->total()` (goes through PowerGrid's real pipeline, so it's correct even with an active search/filter) and `data_get($this->setUp, 'footer.perPage')`, and if `$this->getPage() > $lastPage`, calls `$this->gotoPage($lastPage)` **followed by `unset($this->records)`** — the `unset` is required, not optional: `total()` itself reads the `#[Computed]` `$this->records` property, which memoizes the count for the *old* (pre-correction) page for the rest of the request; without busting that cache, `render()` would still paint the stale, now-empty page even though `getPage()` was already fixed.
  - **Three call sites, three different Livewire hooks, on purpose:** `clampPageToValidRange()` runs after any in-session delete (see `performDelete()` below), catching a delete that empties the current page. `HasPowerGridBehavior::mountHasPowerGridBehavior()` calls it again on every fresh page load (catches a hand-edited `?page=` in the URL — Livewire hydrates query-string-bound properties, including `page`, *before* `mount()` runs, so `getPage()` already reflects the URL by the time this fires). `HasPowerGridBehavior::updatedHasPowerGridBehavior(string $property, mixed $value)` unconditionally `gotoPage(1, ...)`s whenever `$property === 'setUp.footer.perPage'` (the per-page dropdown's `wire:model.live` target) — deliberately *not* a clamp here, since changing how many rows fit per page should always land you back at the start, not leave you stranded mid-list even when the new page count would technically still contain the old page number.
  - **`performDelete(int $id)` (2026-08-17) absorbs all 6 tables' delete handlers into `HasPowerGridBehavior` itself, via the same `#[On('{propertyName}')]` dynamic-placeholder technique used for the News managers** (`#[On('{deleteEvent}')]` — see `HandlesEmbeddedManager` above for the mechanism). Every `Table.php`'s `#[On('delete{X}')] public function delete{X}(int $xId): void { guardSave check → {Model}::whereKey($id)->delete() → clampPageToValidRange() → notify }` was the same 6-line shape, differing only in model class, the id-param name, and the toast noun — now just `protected string $modelClass`, `protected string $itemNoun`, and **`public string $deleteEvent`** (must be `public`, not `protected` — same reason `$managerEventKey`/`$listColumns` had to be: Livewire's placeholder resolver reads the property via `data_get($component, $name)` from *outside* the class, so a `protected` `$deleteEvent` fails silently into the resolver's "unable to evaluate" exception, a real 500 hit and fixed live while building this). Two outliers get one-line hook overrides instead of keeping their own full method: `Admins\Table::beforeDelete(int $id): bool` returns `$id !== auth('admins')->id()` (the self-delete guard — `actions()` already hides the button for your own row, this is defense-in-depth against a directly-dispatched event), `Roles\Table::afterDelete(): void` fires the extra `admin-access-updated` dispatch. The `deleteIconButton()` call in each table's own `actions()` also switched from a hardcoded literal (`'deleteUser'`) to `$this->deleteEvent`, and the dispatched param key standardized to a plain `id` everywhere (was `userId`/`adminId`/`roleId`/`authorId`/`productId`/`newsPostId`) — one source of truth for the event name instead of two places that had to match by hand.
  - **Why `mountHasPowerGridBehavior()`/`updatedHasPowerGridBehavior()`, not plain `mount()`/`updated()`:** Livewire's lifecycle dispatcher (`SupportLifecycleHooks`) calls two independent things per hook — `callHook($name)`, which invokes whatever method PHP resolves `$name` to (normal inheritance/trait rules, the same mechanism that caused the `HasAccessControl`-default-`mount()` incident documented above), **and separately** `callTraitHook($name)`, which reflects over every trait the class uses and calls a method literally named `{$name}{TraitBasename}` on each one (e.g. `mountHasPowerGridBehavior`), regardless of what plain `mount()`/`updated()` resolve to. Naming a trait hook method this way means it runs as a genuinely independent, additive hook — it can never shadow `PowerGridComponent`'s own `mount()`/`updated()`, so there's no `parent::` call to remember and no risk of quietly skipping PowerGrid's internal setup the way the earlier incident did. **Any future trait method meant to hook into a Livewire component's lifecycle without touching what `mount()`/`updated()`/`boot()`/etc. resolve to should use this `{hook}{TraitBasename}` naming, not override the plain hook name.**
